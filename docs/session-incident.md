# تشخیص «خروج از سشن» در برابر قطع صدای ویس‌کال

این دستورات **فقط خواندنی** هستند و نه کلاینت MTProto جدید باز می‌کنند، نه سشن/رمز را چاپ می‌کنند. روی سروری که پروژه با `docker compose` اجرا می‌شود، در پوشهٔ پروژه اجرا کنید. شناسه‌های `846` (سفارش) و `112` (اکانت) را در صورت نیاز عوض کنید. تا تعیین تکلیف سفارش فعال، `up -d --build`، `restart`، `down`، `reset_stuck_orders` و «بازیابی دسته‌جمعی» اجرا نکنید.

## ۱) وضعیت سرویس، پورت‌ها و تشخیص آفلاین سشن‌های ذخیره‌شده

```sh
cd /path/to/tgcallbot
# آیا بات/وارپ/DB/Redis زنده‌اند و پورت DB هنوز عمومی است؟
docker compose ps --format 'table {{.Service}}\t{{.State}}\t{{.Ports}}'
# فقط رمزگشایی محلی و شمارش/هشِ یک‌طرفه؛ هیچ اتصال تلگرام یا تغییر DB ندارد.
docker compose exec -T bot python tools/session_audit.py --bot-id 1
# شمارش رخدادها با برچسب‌های ثابت؛ raw log/exception/session/شماره چاپ نمی‌شود.
docker compose exec -T bot python tools/voice_incident_summary.py --order 846 --minutes 120
docker compose exec -T bot python tools/voice_incident_summary.py --account 112 --minutes 120
```

`inactive/dead` یک **پرچم پایگاه‌داده** است، نه اثبات باطل‌بودن کلید. آمار `duplicate-key` در audit فقط همسان‌بودن کلیدهای *ذخیره‌شده* میان ربات/نمایندگی را نشان می‌دهد؛ صحت زندهٔ آن‌ها را اثبات نمی‌کند. `durable_live` شمارندهٔ اسلات ثبت‌شده است و پیوستگی UDP را تضمین نمی‌کند. `native_binding={present,missing,unknown}` مشاهدهٔ بایندینگ محلی موتور است (پس از دو چرخه قدیمی می‌شود)، نه اثبات بسته‌های رسانه در سرور تلگرام؛ `MEDIA_LOST` نیز به‌تنهایی به معنای باطل‌شدن سشن نیست.

## ۲) خلاصهٔ خواندنی از DB، بدون session_string، لینک یا اطلاعات پرداخت

دستورات زیر فقط ستون‌های بی‌خطر و تعدادها را برمی‌گردانند؛ `psql` از متغیرهای **داخل کانتینر DB** استفاده می‌کند (نه رمز تایپ‌شده در خط فرمان). برای همهٔ آن‌ها `-X` یعنی بدون فایل تنظیمات کاربر.

```sh
docker compose exec -T db sh -lc 'psql -X -qAt -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT bot_id, account_status, spam_status, count(*) FROM telegram_accounts GROUP BY 1,2,3 ORDER BY 1,2,3"'
docker compose exec -T db sh -lc 'psql -X -qAt -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT id, bot_id, account_status, spam_status, last_health_check FROM telegram_accounts WHERE id=112"'
docker compose exec -T db sh -lc 'psql -X -qAt -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT id, status, accounts_count, duration_minutes, (price_paid>0) AS paid, (started_at IS NOT NULL) AS timer_started FROM orders WHERE id=846"'
docker compose exec -T db sh -lc 'psql -X -qAt -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT account_id, count(*) FROM voice_join_attempts WHERE order_id=846 GROUP BY account_id ORDER BY account_id"'
# فقط کد عددی خطا و تعداد؛ پیام خطا/کلید/لینک چاپ نشود:
docker compose exec -T db sh -lc 'psql -X -qAt -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT COALESCE(telegram_error_code::text, '\''unknown'\''), count(*) FROM voice_join_attempts WHERE order_id=846 GROUP BY 1 ORDER BY 1"'
```

`last_health_check` زمان آخرین ارزیابی است، **نه** زمان غیرفعال‌شدن. `voice_join_attempts` برای اکانتی که هرگز انتخاب نشده رکورد ندارد؛ نبود آن نشانهٔ ابطال سشن نیست. دربارهٔ سفارش فعال چیزی در DB تغییر ندهید.

## ۳) شبکهٔ DNS/UDP و WARP: فقط مقدمات، نه اثبات WebRTC

```sh
# این دستورات فقط به DNS عمومی UDP/53 درخواست می‌دهند؛ به تلگرام وصل نمی‌شوند.
python3 tools/check_udp.py
docker compose exec -T bot python tools/check_udp.py
# وجود تونل و پاسخ پروکسی WARP، فقط پیش‌شرط اتصال است:
docker compose exec -T warp sh -lc 'test -d /sys/class/net/CloudflareWARP && echo WARP_TUN_PRESENT || echo WARP_TUN_MISSING'
docker compose exec -T warp sh -lc 'curl -fsS --socks5 127.0.0.1:1080 https://cloudflare.com/cdn-cgi/trace | grep "^warp="'
```

DNS/UDP53 سالم، `warp=on` و `health=healthy` **هیچ‌کدام** UDP مربوط به مدیای تلگرام/کیفیت WebRTC را اثبات نمی‌کنند. اگر فقط یک DNS resolver پاسخ داد خروجی کد ۰ است اما مشکل ویس هنوز ممکن است؛ اگر هیچ‌کدام پاسخ نداد، نتیجه نامشخص است نه اثبات بسته‌بودن تمام UDP.

## ۴) تشخیص علت و بازیابی کم‌ریسک

- `media_transport_lost` یا `confirmed_disconnect` بدون خطای صریحِ احراز هویت یعنی **قطع حضور/رسانه**؛ خودبه‌خود معادل revoke یا logout نیست. اگر این‌ها زیادند، مسیر UDP، مصرف CPU/FD، WARP و رویداد `media_restored` را مقایسه کنید.
- `AUTH_KEY_DUPLICATED` (406) یعنی برخورد استفاده از یک کلید؛ مشخص نمی‌کند کلید اکنون معتبر است یا نه. کپی‌های سشن بین ربات/نمایندگی، برنامهٔ دیگر و نمونه‌های قدیمی را بررسی کنید، اما برای همان کلید probe موازی/دسته‌جمعی نزنید.
- فقط خطای صریح `SESSION_REVOKED`/`AUTH_KEY_UNREGISTERED`/`AUTH_KEY_INVALID` یا RPC 401 احراز هویت، دلیلِ نیاز احتمالی به **ورود مجدد با کلید تازه** است. برای کلید واقعاً باطل‌شده «نگه‌داشتن سشن» با تغییر کد ممکن نیست.
- یک اکانت `inactive` را **پس از خالی‌شدن ویس فعال همان کلید** از داخل رابط ادمین ربات با گزینهٔ «بازیابی همین اکانت» بررسی کنید. این مسیر در همان فرایند ربات مالکیت کلید را چک می‌کند، فقط `get_me()` و قطع تأییدشده انجام می‌دهد و تنها همان رکورد/کلید را فعال می‌کند. اجرای Python جداگانه یا `docker compose exec bot` برای پروب زنده، گارد مالکیت درون‌فرایندی را دور می‌زند؛ انجام ندهید.

## ۵) محدودیت‌های اصلاحات و سفارش پرداخت‌شده

این کد در محیط آفلاین بررسی شده و **روی سرور شما مستقر یا در تماس واقعی آزموده نشده است**. چند مسیر قابل‌اثباتِ خروج ناخواسته از کد محافظت شده‌اند: بازسازی موتور پس از خطای موقتِ query که قبلاً همهٔ تماس‌های همان اکانت را ترک می‌کرد؛ پاک‌سازی یک سفارش در حالی که اسلات سفارش دیگری برای همان اکانت/همان چت ثبت است؛ و تفسیر نادرست شناسهٔ منفیِ چت به‌عنوان «عدم حضور». وضعیت سشنِ مشترک در جدول نیز فقط برای همان سفارش به‌روز می‌شود. خطای شروع موتور دیگر به ساخت نمونهٔ دوم روی کلیدِ درحال‌استفاده منجر نمی‌شود. سالم‌بودن صدای UDP/WebRTC و معتبر ماندن کلیدهای ذخیره‌شده نیازمند شواهد **روی همان سرور** است؛ تست آفلاین چنین ادعایی نمی‌کند.

**سیاست اعلام‌شدهٔ بهره‌بردار:** تعداد اکانتْ مبنای کاهش مبلغ نیست. سفارش ۵۰تایی با حداکثر اکانت قابل‌استفاده (حتی ۲۰ یا یک اکانت) اجرا می‌شود؛ به‌محض پیوستن حداقل یک اکانت، هزینه بر پایهٔ **قیمت کامل پلن و زمان مصرف‌شده** محاسبه می‌شود، نه نسبت تعداد اکانت‌ها. سفارش **جدید** فقط اگر حتی یک اکانت با پرچم `active` هم نباشد پیش از کسر اعتبار رد می‌شود؛ این پرچمْ موفقیت join یا رسانه را تضمین نمی‌کند. کسر اعتبار/ثبت سفارش/ثبت تراکنش در یک تراکنش DB انجام می‌شوند و کلیک تکراریِ یک کاربر برای همان پلن/مقصد/زمان‌بندی در یک پنجرهٔ کوتاه دوباره شارژ نمی‌شود. لغوِ دستیِ کاربر/ادمین با قفل رکورد سفارش و کیف پول، **فقط یک‌بار** تسویه می‌شود؛ شارژِ تأییدشدهٔ درگاه نیز تنها یک‌بار با تغییر وضعیت پرداخت در همان تراکنش ثبت می‌شود. `started_at` فقط یک‌بار و فقط برای سفارش `running` در DB ثبت می‌شود؛ قطعی DB با ساعتِ محلی، شروع پولیِ جعلی ایجاد نمی‌کند. اگر هیچ اکانتی واقعاً نپیوندد، تایمر پولی شروع نمی‌شود؛ مسیر خطا **وضعیت `failed` و عودتِ زمانِ استفاده‌نشده را اتمیک و فقط یک‌بار** ثبت می‌کند. اگر DB در لحظهٔ تسویه قطع باشد، وضعیت/اعتبار دست‌نخورده می‌ماند و نیاز به رسیدگی بهره‌بردار بعد از بازیابی DB است؛ خودسرانه مبلغ را دوباره برنگردانید. اگر پس از کسر اعتبار، شروع executor شکست بخورد، شمارهٔ سفارش برای پیگیری به خریدار اعلام می‌شود؛ چنین سفارش `pending` را بدون بررسی وضعیت زنده دوباره ثبت نکنید. دربارهٔ سفارش ۸۴۶ بدون بررسی DB زنده وضعیت یا اعتبار را تغییر ندهید.

**مهم پیش از استقرار:** در شروع برنامه `DatabaseManager.reset_stuck_orders()` تمام سفارش‌های `running` را `stopped` می‌کند؛ بنابراین حتی اگر خودتان این تابع را دستی اجرا نکنید، راه‌اندازی مجدد نسخهٔ جدید در میانهٔ سفارشِ در حال اجرا می‌تواند آن را متوقف کند. صبر کنید سفارش ۸۴۶ تعیین‌تکلیف شود؛ قبل از هر `up/restart` از وضعیت سفارش، پرداخت، `started_at`، اتصال‌ها و زمان‌بندی آن روی سرور نسخهٔ پشتیبان امن بگیرید (بدون افشای سشن/رمز)، و فقط با برنامهٔ استقرارِ موردتأیید بهره‌بردار اقدام کنید.

### نکتهٔ امنیتی فوری

تا وقتی نسخهٔ جدید Compose **پس از اتمام سفارش فعال** مستقر نشده، ممکن است PostgreSQL همچنان روی `0.0.0.0:5432`/`[::]:5432` در دسترس اینترنت باشد. همین حالا دسترسی ۵۴۳۲ را از فایروال **ارائه‌دهنده** فقط به مبدأ مدیریت محدود کنید. تغییر فایل Compose در این مخزن روی سرور اثر ندارد؛ DB را وسط سفارش فقط برای بستن پورت بازآفرینی نکنید. خروجی کامل `.env`، `docker compose config`، `pg_dump`، session_string، log خام یا آدرس/رمز دیتابیس را به اشتراک نگذارید.
