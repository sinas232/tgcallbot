# نسخهٔ ۲.۲.۹ — حسابداری سفارش، رسید واحد و جلوگیری از گزارش متناقض

## قرارداد مالی

1. هنگام تأیید، **کل مبلغ** یک بار کسر می‌شود. ساخت سفارش، بدهکارکردن کیف پول،
   تراکنش خرید و کلید یکتای همان پیام تأیید در یک تراکنش PostgreSQL هستند.
   با شکست commit هیچ‌کدام ثبت نمی‌شوند. فرم قدیمی نمی‌تواند مشخصات سفارش تازه را بخرد.
2. هنگام لغو عادی:
   - `مصرف = مبلغ کل × ثانیهٔ خدمت ارائه‌شده ÷ ثانیهٔ خریداری‌شده`
   - `عودت = مبلغ کل − مصرف`
   - `موجودی پس از لغو = موجودی قبل از لغو + عودت`
3. محاسبه با Decimal است؛ مبلغ مصرف فقط **یک بار** با ROUND_HALF_UP به
   **۰٫۰۱ تومان** گرد می‌شود. عودت از تفاضل محاسبه می‌شود، نه با گردکردن مستقل.
   زمان به دقیقهٔ کامل گرد نمی‌شود و حداکثر به مدت خریداری‌شده محدود است.
   ستون‌های مالی قدیمی برای سازگاری مهاجرت مخرب نشده‌اند؛ عملیات جدید مبالغ را
   قبل از ذخیره و جمع/تفریق به دو رقم اعشار نرمال می‌کنند.
4. وضعیت نهایی، واریز کیف پول، تراکنش عودت و رسید `OrderSettlement` با هم commit
   می‌شوند. تکرار کلیک همان رسید را برمی‌گرداند، نه واریز مجدد.
5. لغو و اتمام روی همان ردیف سفارش قفل می‌گیرند؛ فقط یک مسیر برنده است.
   تکمیل عادی هزینهٔ دوباره کم نمی‌کند.

مثال: سفارش دو ساعتهٔ ۱۲۰٬۰۰۰ تومان، لغو پس از ۳۰ دقیقهٔ خدمت ثبت‌شده:
**مصرف ۳۰٬۰۰۰، عودت ۹۰٬۰۰۰ تومان**. اگر موجودی پیش از خرید ۲۰۰٬۰۰۰ باشد،
پس از خرید ۸۰٬۰۰۰ و پس از این لغو ۱۷۰٬۰۰۰ تومان است.

### استثنای صریح ادمین

قابلیت موجود «لغو بدون عودت توسط ادمین» حذف نشده است. در این انتخاب، عودت
صفر است؛ رسید جداگانه «هزینهٔ خدمت ارائه‌شده» و «مبلغ استفاده‌نشدهٔ نگه‌داشته‌شده»
را ثبت می‌کند. کل مبلغ نگه‌داشته‌شده نباید به‌اشتباه زمان مصرف واقعی نامیده شود.
لغو معمول کاربر همیشه از فرمول تناسبی استفاده می‌کند.

## زمان قابل‌صورتحساب

- انتظار، رزرو آینده، ساخت/ورود اکانت‌ها و خروج/پاک‌سازی پایان سفارش جزو مدت پولی نیستند.
- سفارش مدتی با تعداد ناقص وارد زمان پولی نمی‌شود؛ اگر build نتواند تعداد را
  تأمین کند، از مسیر تسویهٔ اتمیک بسته می‌شود. سفارش حجمی، سهم تعداد موفق را حساب می‌کند.
- در ویس، زمان هنگامی جلو می‌رود که تعداد موردنیاز در وضعیت تاییدشدهٔ JOINED
  و در active_calls باشد. وضعیت تشخیص‌داده‌شدهٔ قطع/نامشخص/کمبود تعداد، زمان را
  متوقف می‌کند؛ جایگزینی‌های بعدی حتی برای کمتر از ۶۰ ثانیهٔ باقی‌مانده ممکن‌اند.
- ساعت monotonic است، نه ساعت دیواری. نمونه‌برداری محلی تقریباً یک‌ثانیه‌ای و
  checkpoint معمولاً پنج‌ثانیه‌ای است. تشخیص وضعیت شبکه تابع مانیتور ویس است؛
  این به معنی اطلاع آنی و بی‌خطا از تمام قطعی‌های فیزیکی نیست.
- بازهٔ بلندِ بدون مشاهده به ضرر کاربر محاسبه نمی‌شود. در قطع ناگهانی فقط
  checkpoint ذخیره‌شده معتبر است؛ معمولاً تا حدود پنج ثانیهٔ اخیر هدیه می‌شود.
  اختلال طولانی دیتابیس ممکن است بازهٔ بیشتری را رایگان کند، نه بدهکار کند.
- لغو زنده از snapshot ساعت همان executor استفاده می‌کند؛ رسید پس از commit
  تغییر نمی‌کند. ماندهٔ روی رسید، موجودی **لحظهٔ تسویه** است، نه ماندهٔ جاری پس
  از تراکنش‌های بعدی. نمایش کیف پول/ادمین/شارژ نیز اعشار را پنهان نمی‌کند.

## ریشهٔ گزارش‌های تکراری و متناقض چه بود؟

- جاب انقضای قدیمی با `created_at` می‌توانست سفارش درحال build را تمام‌شده فرض کند.
- همان جاب ابتدا executor را cancel می‌کرد و سپس جداگانه گزارش completed می‌فرستاد.
- مسیر `_finish_order` نتیجهٔ انتقال وضعیت را بررسی نمی‌کرد؛ بازندهٔ رقابت لغو
  هم می‌توانست گزارش اتمام بدهد.
- fallback ارسال Markdown همهٔ خطاها، حتی timeout مبهم را دوباره می‌فرستاد.
- عودت startup خارج از تراکنش/رسید اتمیک بود؛ pending تسویه‌شده می‌توانست باز بماند.

در این نسخه پایان زمان فقط با تایمر خدمت executor انجام می‌شود. گزارش نهایی
کانال، کلید یکتای مشترک بین cancelled/completed/failed دارد. لغو تکراری cleanup
را دوباره cancel نمی‌کند؛ تسک‌های ورود فرزند قبل از پاک‌سازی drain می‌شوند.

### مرز تضمین ارسال تلگرام

**عملیات مالی اتمیک و idempotent است؛ شبکهٔ تلگرام exactly-once سرتاسری نمی‌دهد.**
برای جلوگیری از پیام تکراری، گزارش قبل از ارسال یک claim پایدار می‌گیرد؛ timeout
مبهم خودکار resend نمی‌شود. فقط خطای قطعی parse entities مجاز به fallback متنی است.
اگر پردازش بین claim و ارسال قطع شود یا پاسخ پیام گم شود، گزارش ممکن است نرسد؛
رسید مالی محفوظ است و دوباره از مسیر لغو کاربر/ادمین قابل مشاهده است.
`order_reports.state` ارسال تأییدشده (`sent`) یا ارسال آغازشده/نامطمئن را نشان می‌دهد.
این مرز را نباید با «تضمین دریافت تمام پیام‌ها» اشتباه گرفت.

## ری‌استارت و سابقهٔ قدیمی

**این نسخه بازیابی مالی را اصلاح می‌کند، نه ادامهٔ اتصال پس از restart.**
سفارش قطع‌شده همچنان طبق سیاست فعلی با مصرف ذخیره‌شده تسویه می‌شود؛ زمان خاموشی
از کیف پول کم نمی‌شود. ادامهٔ خودکار باقی‌ماندهٔ خدمت نیازمند تغییر جداگانهٔ
چرخهٔ اجرای سفارش است و هنوز پیاده‌سازی نشده است.

برای سفارش قدیمی running که checkpoint ندارد و executor زنده هم ندارد، زمان
قبل از قطع را نمی‌توان ساخت: سیاست محافظه‌کارانهٔ این نسخه عودت کامل است.
سفارش‌های تاریخی stopped/completed و رسیدهای قبلی خودکار بازنویسی نمی‌شوند.
تشخیص/اصلاح عودت‌های تکراری قدیمی نیازمند ممیزی شناسهٔ سفارش و تراکنش‌هاست؛
از کاربران به‌صورت حدسی پول پس گرفته نمی‌شود.

## نصب امن

- روی **یک نمونهٔ فعال ربات** مستقر کنید؛ هم‌زمان دو نسخه را روی یک دیتابیس اجرا نکنید.
- ابتدا تعمیرات را روشن کنید تا سفارش تازه پذیرفته نشود؛ سفارش‌های جاری تمام شوند.
  نسخهٔ قدیمی هنگام shutdown هنوز رفتار قدیمی خود را دارد؛ برای آپدیت آن را وسط سفارش قطع نکنید.
- پشتیبان معتبر دیتابیس بگیرید و `.env`، pickleها و volumeها را حفظ کنید.
- هرگز `down -v`، reset اجباری یا اسکریپت restart مخرب اجرا نکنید.

```bash
cd /opt/tgcallbot
git status --short
git branch --show-current
# باید روی شاخهٔ arena/01a0b5c9-tgcallbot باشید؛ تغییرات محلی را دور نریزید.
git pull --ff-only origin arena/01a0b5c9-tgcallbot
# فقط پس از اتمام سفارش‌های جاری:
docker compose up -d --build --no-deps bot
docker logs --since 5m --tail 150 telegram_bot_container
```

سه جدول افزوده (`order_billing`, `order_purchases`, `order_reports`) با init_db
ایجاد می‌شوند و در بکاپ JSON نیز هستند. سقف RAM/CPU دوباره اضافه نشده است:

```bash
docker inspect --format 'Memory={{.HostConfig.Memory}} NanoCpus={{.HostConfig.NanoCpus}} CpuQuota={{.HostConfig.CpuQuota}}' telegram_bot_container
```

## تست پذیرش قبل از خاموش‌کردن تعمیرات

با سفارش آزمایشی و دسترسی ادمین:
1. موجودی قبل از خرید را یادداشت کنید؛ دوبار تأیید همان پیام فقط یک بدهی داشته باشد.
2. لغو قبل از شروع زمان پولی: عودت کامل، یک تراکنش و یک گزارش کانال.
3. لغو وسط زمان پولی: مبلغ اولیه = مصرف + عودت؛ موجودی = قبل خرید − مصرف.
4. دوباره همان لغو را بزنید: همان کد عودت، بدون تغییر موجودی یا گزارش کانال جدید.
5. اتمام طبیعی: فقط completed؛ بدون لغو/عودت/برداشت دوباره.
6. هم‌زمانی لغو کاربر و ادمین: یک رسید مالی. انقضای ساعت دیواری نباید build را ببندد.
7. کیف پول و رسید، بخش اعشاری احتمالی را یکسان نشان دهند.

تست‌های خودکار شامل PostgreSQL واقعی با schema جدا، ۲۰ درخواست هم‌زمان، rollback
خرید/عودت، رقابت اتمام/لغو، توقف واقعی تسک executor، checkpoint زمان خاموشی، حفظ
رسیدها در backup/restore و timeout تلگرام هستند. تماس واقعی تلگرام در این محیط
آزمایش نشده و تست پذیرش روی سرور لازم است.

نتیجهٔ نهایی این تغییر: **۳۰۲ تست موفق، بدون skip**؛ شامل **۲۷ تست PostgreSQL واقعی** و ۳۴ تست جدید مالی/چرخهٔ اجرا. `compileall` و `git diff --check` نیز موفق بودند.
