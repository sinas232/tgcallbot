# تحویل نسخهٔ کامل ۲.۳.۱۳ (با حفظ امکانات نسخهٔ ۲.۳.۱۲)

این نسخه از **شاخهٔ `arena/01a0ccf5-tgcallbot` و commit `0a627e1`** (نسخهٔ ۲.۳.۱۲) ساخته شده است؛ نه از `main` قدیمی با commit `3f76f05` (۲.۲.۳). GitHub Release قابل مشاهده در زمان بررسی ۲.۱.۰ بود؛ شمارهٔ نسخهٔ کد، وضعیت شاخه و انتشار رسمی GitHub سه مفهوم متفاوت‌اند. این سند فهرست قابلیت‌های تحویلی و استثناهای آگاهانه را مشخص می‌کند.

## تطبیق با آخرین شاخهٔ کامل

تمام ۸۷ فایل رهگیری‌شدهٔ مبنای ۲.۳.۱۲ در نسخهٔ تحویلی باقی‌اند. در آغاز ادغام، ۷۷ فایل با آن نسخه بایت‌به‌بایت یکسان و فقط ۱۰ فایل تغییرکرده بودند؛ هیچ فایل مبنا مفقود نبود. مقایسهٔ AST نشان داد هیچ تعریف تابعی از `handlers/admin_handlers.py`، `handlers/order_handlers.py`، `main.py`، `services/order_executor.py` یا `services/voice_call_manager.py` حذف نشده است. تفاوت زیادِ اولیه با `main` به‌معنی حذف قابلیت نبود: پوشهٔ کاری از checkout قدیمی شروع شده بود و فایل‌های نسخهٔ جدید هنوز در commit محلی ثبت نشده بودند. شاخهٔ جاری به commit نسخهٔ کامل رسانده شد **بدون دست‌زدن به فایل‌های کاری**؛ اصلاحات بعدی روی آن باقی ماندند.

**استثنای عمدی:** فایل `services/capacity_planner.py` و گاردِ رد سفارش بزرگ‌تر از ظرفیت از **نسخهٔ ۲.۳.۱** حذف شده بودند، و در نسخهٔ مرجع ۲.۳.۱۲ نیز وجود ندارند. بازگرداندن قفل ظرفیت با درخواست صریح «پلن ۵۰تایی حتی با ۲۰ اکانتِ قابل‌استفاده اجرا شود» در تضاد است؛ بنابراین آن را بازنگرداندیم. تعداد حساب‌های وصل‌شده قیمت را کم نمی‌کند. سفارش تازه فقط وقتی پرچم `active` حتی برای یک اکانت وجود ندارد **پیش از کسر اعتبار** رد می‌شود؛ پرچم دیتابیسْ سلامت واقعی سشن یا پیوستن به ویس را ثابت نمی‌کند.

## اصلاحات افزوده بدون کاستن از قابلیت‌ها

- خرید سفارش با شارژ کیف پول و ledger در یک تراکنش ثبت می‌شود؛ لغو کاربر/ادمین و شکستِ بدون join به‌صورت یک‌باره و اتمیک تسویه می‌شوند؛ callback تکراری درگاه دوباره شارژ نمی‌کند. در صورت عدم امکان ثبت `started_at`، زمانِ پولی با ساعت محلی جعل نمی‌شود.
- جاب سفارش زمان‌بندی‌شده فقط وضعیت `scheduled` واقعی را به `running` انتقال می‌دهد. اگر کاربر هم‌زمان سفارش را لغو و عودت کرده باشد، کارگر ساخته نمی‌شود و اعلانِ «خدمت شروع شد» ارسال نمی‌شود.
- قطع اتصال محلی WebRTC یا خطای موقت فهرست شرکت‌کنندگان به‌تنهایی ابطال سشن تلقی نمی‌شود. peer هر کانال به اکانت خودش محدود است؛ پایان سفارشِ مشترک موتور سفارش دیگر را قطع نمی‌کند. شمارندهٔ `native_binding` از حضور ثبت‌شده جداست و آزمایش DNS/UDP-53 هیچ تضمینی دربارهٔ مدیای تلگرام نمی‌دهد.
- پورت دیتابیس PostgreSQL و Redis در حالت عیب‌یابی host فقط به loopback هاست bind می‌شود. ابزار `tools/voice_incident_summary.py` برای خلاصهٔ خواندنی رخدادها اضافه شده است.

## اعتبارسنجی و راه استفاده

```sh
# اجرای تست‌ها بدون اتصال Telegram یا دیتابیس واقعی (از پوشهٔ پروژه)
python -m unittest discover -s tests
python -m compileall -q database.py main.py handlers services tools tests
# راهنمای ارزیابی رخدادهای زنده، بدون تغییر وضعیت اکانت یا سفارش:
cat docs/session-incident.md
```

تست‌های آفلاین برای منو/ضداسپم، مسیرهای مالی، سشن، ویس، عودت، سفارش با استخر کوچک‌تر و ترتیب لغو/اجرای سفارش زمان‌بندی‌شده وجود دارند؛ یک تست ffmpeg در محیطی که این ابزار نصب نیست skip می‌شود. **موفقیت این تست‌ها اثبات معتبر بودن ۲۵ سشن غیرفعال، UDP سرور، حضور پایدار تماس یا نتیجهٔ سفارش واقعی ۸۴۶ نیست.** نه DB زنده بررسی شده و نه سفارش ۸۴۶ دستکاری شده است.

### پیش از استقرار

در شروع برنامهٔ فعلی `DatabaseManager.reset_stuck_orders()` سفارش‌های `running` قدیمی را `stopped` می‌کند؛ بنابراین **وسط سفارش فعال، `up/restart/down` نزنید**. فقط پس از ثبت وضعیت واقعی سفارش‌ها و هماهنگی با بهره‌بردار از شاخه/بستهٔ کامل استقرار دهید. [راهنمای رخداد و استقرار](session-incident.md) و [ممیزی سشن](session-safety.fa.md) را بخوانید؛ بازیابی دسته‌جمعی اکانت‌های `inactive` یا اجرای MTProto probe در پردازهٔ مستقل ممنوع است. این نسخه هنوز به `main` merge یا روی سرور نصب نشده است.
