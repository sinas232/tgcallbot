# جلوگیری از تداخل سشن و تشخیص ۱ فعال از ۲۶ اکانت (نسخهٔ ۲.۳.۱۲)

## چرا این مشکل با «فقط یک‌بار اجرای ربات» هم رخ می‌دهد؟

هر سشن Pyrogram حاوی یک **کلید احراز هویت تلگرام** است. ربات می‌تواند در **همان یک پردازه** دو بار با آن کلید وصل شود؛ برای مثال، «کپی اکانت‌ها برای نمایندگی» دو ردیف با شناسه‌های متفاوت، ولی با همان Session String می‌سازد. مسیر ورود با شماره نیز قبلاً فقط `connect()` می‌کرد، اما هنگام ذخیره، `stop()` صدا می‌زد؛ برای کلاینتی که هنوز `start()` نشده، این کار ممکن بود پیش از `disconnect()` خطا بدهد. کلیدِ ذخیره‌شده در دیتابیس در آن صورت هنوز با اتصال ورود فعال بود.

**نکتهٔ تشخیصی:** لاگِ صرفاً «ربات اجرا شد» یا خطای `AUTH_KEY_DUPLICATED` منشأ دقیق اتصال دوم، یا سالم‌بودن فعلی کلید را ثابت نمی‌کند. تلگرام ممکن است پس از تداخل، کلید را باطل کرده باشد. توضیح قدیمیِ نسخهٔ ۲.۳.۹ که ۴۰۶ را حتماً به «سرور دوم» و «کلید سالم» نسبت می‌داد، قابل اتکا نبود.

## محافظت‌های نسخهٔ جدید

- قفل رزرو بر **اثر انگشتِ خودِ کلید** است، نه شناسهٔ ردیف یا متنِ رمز‌شدهٔ سشن. کپی یک کلید به ربات اصلی و نمایندگی، اتصال هم‌زمان دوم را در همان پردازه مسدود می‌کند. خود کلید یا Session String در لاگ نوشته نمی‌شود.
- مسیرهای ورود با شماره، import سشن، پروب سلامت، گرم‌کردن کلاینت، ورود به ویس و خروج/خاموشی از یک قرارداد قطع اتصال پیروی می‌کنند. سشن جدید تا زمانی که اتصال ورود واقعاً قطع نشده، در دیتابیس ذخیره نمی‌شود. برای ورود با `connect()`، مستقیماً `disconnect()` استفاده می‌شود.
- هنگام timeout یا لغو موج، رزرو کلید **تا قطع تأییدشده** باقی می‌ماند؛ انقضای زمانی رزرو، اتصال زنده را آزاد نمی‌کند. قطع نامطمئن یعنی قرنطینهٔ همان کلید در این پردازه.
- یک قفل فایل روی مسیر ثابت پروژه و یک **قفل سراسری PostgreSQL** پیش از راه‌اندازی اکانت‌ها گرفته می‌شود. رباتِ دومِ مجهز به این نسخه و متصل به همان دیتابیس بدون وصل‌شدن به اکانت‌ها متوقف می‌شود. اگر اتصال اختصاصیِ نگه‌دارندهٔ قفل DB از دست برود، ربات برای حفاظت از کلیدها بلافاصله خارج می‌شود. پیش از استفاده از سشن‌ها پس از ری‌استارت، ۱۰ ثانیه فرصت پایان اتصال‌های TCP قبلی داده می‌شود.
- `AUTH_KEY_DUPLICATED` (۴۰۶) خودبه‌خود اکانت را `inactive` نمی‌کند؛ برای همان سفارش retry متوقف و در گزارش «تداخل کلید» ثبت می‌شود. فقط ابطال صریح (مانند خطای RPC ۴۰۱/`SESSION_REVOKED`) دلیل غیرفعال‌سازی خودکار است. **این سیاست کلید واقعاً باطل‌شده را احیا نمی‌کند.**
- باگ تازه‌یافت‌شده: نسخه‌های قبلی عدد `401` را از هر پیام (مثلاً `FloodWait:401` یعنی **۴۰۱ ثانیه انتظار**) معادل ابطال سشن می‌گرفتند و در مسیر سفارش، اکانت را `inactive/dead` می‌کردند. اکنون فقط خطای احراز هویت **صریح** معتبر است؛ در دیتابیس دلیل ثابت و بدون متن حساس ثبت می‌شود. تغییر وضعیت فقط وقتی انجام می‌شود که کلید رمز‌شدهٔ ذخیره‌شده هنوز همان کلید زمان خطا باشد؛ خطای دیررسِ کلید قدیمی نمی‌تواند ورود جدید را غیرفعال کند. ورود جدید همچنین برچسب تاریخی `dead` را پاک می‌کند. **این اصلاح به‌تنهایی وضعیت ۲۵ ردیفِ از قبل غیرفعال را تغییر نمی‌دهد.**
- دکمهٔ کپی Session String از ربات اصلی به نمایندگی، از جمله کلیک روی دکمهٔ قدیمی، غیرفعال شده است. کلیدهای تکراریِ از پیش ذخیره‌شده خودکار حذف یا جایگزین نمی‌شوند؛ برای مصرف هم‌زمان باید با شماره جداگانه وارد شد.

**محدودیت:** قفل PostgreSQL فقط نسخه‌های جدیدی را هماهنگ می‌کند که به همان دیتابیس وصل می‌شوند. فرایند قدیمی، ابزار مستقل یا پنل/فروشندهٔ شخص ثالث ممکن است همچنان همان سشن را استفاده کند. حتی کپی‌های نمایندگی، اگر قرار است هم‌زمان استفاده شوند، باید برای **هر ربات جداگانه** لاگین کنند و کلیدهای متفاوت بگیرند.

## استقرار محتاطانه روی سرور

پیش‌نویس ۲.۳.۱۴ هنوز با برخی تنظیمات تاریخی سازگار نیست؛ [هشدار سازگاری](env-compatibility.fa.md) را بخوانید و [راهنمای استقرار](deploy-final.fa.md) را تا رفع ناسازگاری اجرا نکنید. مستقیم `git pull`/`docker compose stop/up` وسط سفارش فعال نزنید. `reset_stuck_orders()` در بوت، سفارش `running` را `stopped` می‌کند.
راهنمای نهایی قبل از تغییر فایل‌ها، وضعیت سفارش ۸۴۶ و سایر سفارش‌های پولی را
فقط‌خواندنی بررسی می‌کند، بکاپ می‌گیرد و حالت تعمیرات را لازم می‌داند.
حتی اگر برنامه بالا آمد، سلامت سشن‌های واقعی/UDP ثابت نشده است.

اگر `git status` تغییرات محلی دارد، **آن‌ها را بررسی/پشتیبان‌گیری کنید**؛ دستور `git reset --hard` اجرا نکنید. فایل `.env` و کلید `SESSION_ENCRYPTION_KEY` را تغییر ندهید: با کلید جدید، سشن‌های قبلی از دیتابیس قابل رمزگشایی نیستند. نام/آدرس دیتابیس در کانتینر باید همان DB اصلی باشد. اگر `Another tgcallbot instance holds the same DATABASE_URL` دیدید، قفل را دور نزنید؛ نمونهٔ مالکِ همان دیتابیس را شناسایی کنید. هنگام بالا آمدن، ۱۰ ثانیه انتظار بعد از قفل طبیعی است.

قبل از فعال‌کردن سفارش‌های بزرگ، اطمینان حاصل کنید نسخهٔ قدیمی یا برنامهٔ مستقل از سشن‌ها استفاده نمی‌کند. برای مشاهدهٔ پردازه‌ها/کانتینرها بدون نمایش سشن‌ها:

```bash
ps -eo pid,lstart,args | grep -E '[p]ython.*main.py|[t]gcallbot'
docker ps --format '{{.Names}} {{.Image}} {{.Status}}'
```

این دستورها **فقط** نمونه‌ها را نشان می‌دهند؛ بی‌هدف پروسه یا کانتینر را `kill` نکنید. قفل جدید نمی‌تواند نسخهٔ قدیمی‌ای را که آن را نمی‌شناسد متوقف کند. از چاپ Session String یا کلید رمزنگاری در لاگ/چت پشتیبانی خودداری کنید.

## بازیابی اکانت‌های آسیب‌دیده (۲.۳.۱۱)

اگر دیتابیس مثلاً «۱ فعال / ۲۵ غیرفعال و dead» نشان می‌دهد، این **وضعیت
ثبت‌شده** است، نه نتیجهٔ ۲۵ آزمون زنده. نسخه‌های قبلی گاهی ۴۰۶ را به‌اشتباه
`inactive/dead` و حتی `SESSION_REVOKED detected` ثبت می‌کردند. علت تاریخیِ هر
ردیف از داده‌های موجود به‌تنهایی قطعی نیست. **قبل از هر بازیابی یا ری‌لاگین**، ممیزی
فقط‌خواندنی را روی دیتابیس واقعی، داخل کانتینر ربات موجود اجرا کنید:

```bash
cd /opt/tgcallbot
docker compose exec -T bot python tools/session_audit.py --bot-id 1
```

این اسکریپت در پردازهٔ جدا فقط `SELECT` در تراکنش `READ ONLY` انجام می‌دهد؛
**هیچ اتصال MTProto/Telegram باز نمی‌کند**. وضعیت `active/inactive`، برچسب‌های
تاریخی و دسته‌بندی قابلیت رمزگشایی را خلاصه می‌کند و با مقایسهٔ اثر انگشتِ
کلیدِ رمزگشایی‌شده، تعداد ردیف‌های هم‌کلید در خود ربات یا نمایندگی‌های دیگر
را می‌شمارد. نه Session String، نه کلید رمزگذاری و نه شماره‌تلفن چاپ می‌شود.
اگر فایل اسکریپت در کانتینر نبود، ابتدا از آپدیت‌شدن همین شاخه و مسیر
`volumes: .:/app` اطمینان حاصل کنید؛ دستور جایگزینِ پروبِ زنده ننویسید.

تعبیر گزارش: `legacy_SESSION_REVOKED_label_unverified` متن عمومی نسخهٔ قدیمی است،
نه مدرک خطای واقعی Telegram. `strict_auth_error_recorded_after_fix` تنها
برچسب خطای صریح ثبت‌شده **پس از این اصلاح** است. `Duplicate-key groups`
تداخلِ بالقوه در همان دیتابیس را نشان می‌دهد، ولی نبودن گروه تکراری، مصرف
کلید در سرور/ابزار خارجی را رد نمی‌کند. `last_health_check` آخرین بررسی
ثبت‌شده است، **نه الزاماً زمانِ غیرفعال‌شدن**؛ تاریخ داخل Fernet هم زمان ذخیره
است، نه زمان ابطال. نتیجهٔ «کلید قابل‌رمزگشایی» یا «یکتا» **اثبات سلامت زنده نیست**.
پیش از هر پروب، مطمئن شوید همان کلید در جای دیگری هم‌زمان مصرف نمی‌شود؛
اتصال آزمایشی روی کلیدِ مشغول، ریسک ابطال دارد. اگر خروجی ممیزی و بازهٔ
زمانی خطاهای runtime را (پس از حذف اطلاعات حساس) بفرستید، می‌توان مسیر
تاریخیِ غیرفعال‌سازی را دقیق‌تر تفکیک کرد؛ بدون این شواهد، علت همهٔ ۲۵
اکانت را قطعی ندانید. برای خلاصهٔ امنِ فقط‌شمارشِ لاگ runtime (بدون چاپ سطرها،
شماره یا کلید) می‌توانید این فرمان را اجرا کنید؛ محدودیت آن این است که اگر
لاگ‌های دورهٔ وقوع خطا حذف شده باشند، هیچ چیز از گذشته بازسازی نمی‌کند:

```bash
docker compose logs --since=48h --no-color bot | awk '
/AUTH_KEY_DUPLICATED/ { duplicate++ }
/FloodWait[: ]401|FLOOD_WAIT_401/ { wait401++ }
/INSTANCE LOCK LOST|Another tgcallbot instance/ { lock++ }
/disabled: explicit auth failure/ { explicit_auth++ }
END { printf "406_mentions=%d, floodwait401_mentions=%d, lock_events=%d, new_explicit_auth_disables=%d\n", duplicate, wait401, lock, explicit_auth }
'
```

این اعداد **تعداد سطرهای لاگ** هستند، نه تعداد اکانت‌ها؛ صفر بودنشان
سلامت سشن یا نبود تداخل خارج از ربات را اثبات نمی‌کند.

1. مصرف‌کنندگان احتمالی **همان Session String** را شناسایی کنید: ردیف اصلی،
   کپی‌های نمایندگی، سرور/کانتینر قدیمی و ابزارهای شخص ثالث. کلید و
   `SESSION_ENCRYPTION_KEY` را در گزارش یا چت منتشر نکنید.
2. اتصال اضافی را با توقف **کنترل‌شده** ببندید و چند ثانیه صبر کنید. در رباتِ
   مستقرشده با نسخهٔ ۲.۳.۱۱، مسیر «👥 مدیریت اکانت‌ها ← 📋 لیست اکانت‌ها ←
   کارت یک اکانت غیرفعال ← 🧪 بررسی و بازیابی فقط همین اکانت ← تأیید» را بروید.
   این عملیات **داخل همان پردازهٔ ربات** اجرا می‌شود، نه با
   `docker compose exec bot python ...` که از محافظ سشن زنده عبور کند.
3. فقط وقتی `get_me()` موفق شود، قطع اتصال تأیید شود و همان سشن هنوز در همان
   ردیف غیرفعال ذخیره باشد، وضعیت به `active` برمی‌گردد؛ پرچم تاریخی `dead`
   به `unknown` تبدیل می‌شود (**بدون ادعای سلامت اسپم**). اگر خطای ۴۰۶،
   «مشغول»، timeout یا «قطع اتصال نامطمئن» دیدید، وضعیت را عوض نکنید و روی
   همان کلید پشت‌سرهم پروب نزنید. در صورت مشغول بودن ویس، ربات اتصال دوم
   را رد می‌کند؛ این به معنی خروج از سشن نیست.
4. اگر تلگرام `SESSION_REVOKED`/`AUTH_KEY_UNREGISTERED`/`AUTH_KEY_INVALID`/۴۰۱
   داد یا پس از رفع قطعی تداخل کلید همچنان غیرقابل استفاده بود، از مسیر
   «افزودن اکانت» با شماره **دوباره وارد شوید** تا کلید تازه صادر و ذخیره شود.
   کلید قدیمی را با `UPDATE` دستی وضعیت DB یا کپی مجدد Session String
   نمی‌توان تعمیر کرد.
5. برای استفادهٔ هم‌زمان یک اکانت در دو ربات (اصلی/نمایندگی)، در هر ربات
   جداگانه ورود کنید؛ کپی‌کردن همان سشن مجاز نیست. ابتدا با یک اکانت و یک
   سفارش کوچک تست کنید؛ بعد تعداد حاضرها و لاگ را پایش کنید. دکمهٔ سینک
   و حذفِ انبوهِ غیرفعال‌ها موقتاً غیرقابل استفاده است.

آزمون‌های بدون اتصال به تلگرام: `python -m unittest discover -s tests -q`. این آزمون‌ها مسیرهای برنامه را پوشش می‌دهند، اما **سلامت سشن‌های واقعی سرور یا نبودن مصرف‌کنندهٔ شخص ثالث را ثابت نمی‌کنند**.
