# جلوگیری از تداخل سشن و بازیابی اکانت‌ها (نسخهٔ ۲.۳.۱۰)

## چرا این مشکل با «فقط یک‌بار اجرای ربات» هم رخ می‌دهد؟

هر سشن Pyrogram حاوی یک **کلید احراز هویت تلگرام** است. ربات می‌تواند در **همان یک پردازه** دو بار با آن کلید وصل شود؛ برای مثال، «کپی اکانت‌ها برای نمایندگی» دو ردیف با شناسه‌های متفاوت، ولی با همان Session String می‌سازد. مسیر ورود با شماره نیز قبلاً فقط `connect()` می‌کرد، اما هنگام ذخیره، `stop()` صدا می‌زد؛ برای کلاینتی که هنوز `start()` نشده، این کار ممکن بود پیش از `disconnect()` خطا بدهد. کلیدِ ذخیره‌شده در دیتابیس در آن صورت هنوز با اتصال ورود فعال بود.

**نکتهٔ تشخیصی:** لاگِ صرفاً «ربات اجرا شد» یا خطای `AUTH_KEY_DUPLICATED` منشأ دقیق اتصال دوم، یا سالم‌بودن فعلی کلید را ثابت نمی‌کند. تلگرام ممکن است پس از تداخل، کلید را باطل کرده باشد. توضیح قدیمیِ نسخهٔ ۲.۳.۹ که ۴۰۶ را حتماً به «سرور دوم» و «کلید سالم» نسبت می‌داد، قابل اتکا نبود.

## محافظت‌های نسخهٔ جدید

- قفل رزرو بر **اثر انگشتِ خودِ کلید** است، نه شناسهٔ ردیف یا متنِ رمز‌شدهٔ سشن. کپی یک کلید به ربات اصلی و نمایندگی، اتصال هم‌زمان دوم را در همان پردازه مسدود می‌کند. خود کلید یا Session String در لاگ نوشته نمی‌شود.
- مسیرهای ورود با شماره، import سشن، پروب سلامت، گرم‌کردن کلاینت، ورود به ویس و خروج/خاموشی از یک قرارداد قطع اتصال پیروی می‌کنند. سشن جدید تا زمانی که اتصال ورود واقعاً قطع نشده، در دیتابیس ذخیره نمی‌شود. برای ورود با `connect()`، مستقیماً `disconnect()` استفاده می‌شود.
- هنگام timeout یا لغو موج، رزرو کلید **تا قطع تأییدشده** باقی می‌ماند؛ انقضای زمانی رزرو، اتصال زنده را آزاد نمی‌کند. قطع نامطمئن یعنی قرنطینهٔ همان کلید در این پردازه.
- یک قفل فایل روی مسیر ثابت پروژه و یک **قفل سراسری PostgreSQL** پیش از راه‌اندازی اکانت‌ها گرفته می‌شود. رباتِ دومِ مجهز به این نسخه و متصل به همان دیتابیس بدون وصل‌شدن به اکانت‌ها متوقف می‌شود. اگر اتصال اختصاصیِ نگه‌دارندهٔ قفل DB از دست برود، ربات برای حفاظت از کلیدها بلافاصله خارج می‌شود. پیش از استفاده از سشن‌ها پس از ری‌استارت، ۱۰ ثانیه فرصت پایان اتصال‌های TCP قبلی داده می‌شود.
- `AUTH_KEY_DUPLICATED` (۴۰۶) خودبه‌خود اکانت را `inactive` نمی‌کند؛ برای همان سفارش retry متوقف و در گزارش «تداخل کلید» ثبت می‌شود. فقط ابطال صریح (مانند ۴۰۱/`SESSION_REVOKED`) دلیل غیرفعال‌سازی خودکار است. **این سیاست کلید واقعاً باطل‌شده را احیا نمی‌کند.**

**محدودیت:** قفل PostgreSQL فقط نسخه‌های جدیدی را هماهنگ می‌کند که به همان دیتابیس وصل می‌شوند. فرایند قدیمی، ابزار مستقل یا پنل/فروشندهٔ شخص ثالث ممکن است همچنان همان سشن را استفاده کند. حتی کپی‌های نمایندگی، اگر قرار است هم‌زمان استفاده شوند، باید برای **هر ربات جداگانه** لاگین کنند و کلیدهای متفاوت بگیرند.

## استقرار محتاطانه روی `/opt/tgcallbot`

روی سروری که ربات در آن اجراست، پس از انتشار شاخهٔ `arena/01a0ccf5-tgcallbot`:

```bash
cd /opt/tgcallbot
git status --short
git fetch origin arena/01a0ccf5-tgcallbot
# اگر شاخهٔ جدید هنوز روی سرور وجود ندارد:
git switch --track -c arena/01a0ccf5-tgcallbot origin/arena/01a0ccf5-tgcallbot
# اگر قبلاً ساخته شده: git switch arena/01a0ccf5-tgcallbot && git pull --ff-only origin arena/01a0ccf5-tgcallbot

docker compose stop bot
docker compose up -d --build bot
docker compose ps bot
docker compose logs --since=10m --no-color bot | grep -E 'Local singleton lock|Instance database lock|Main Bot Started|running commit|INSTANCE LOCK LOST|AUTH_KEY_DUPLICATED'
```

اگر `git status` تغییرات محلی دارد، **آن‌ها را بررسی/پشتیبان‌گیری کنید**؛ دستور `git reset --hard` اجرا نکنید. فایل `.env` و کلید `SESSION_ENCRYPTION_KEY` را تغییر ندهید: با کلید جدید، سشن‌های قبلی از دیتابیس قابل رمزگشایی نیستند. نام/آدرس دیتابیس در کانتینر باید همان DB اصلی باشد. اگر `Another tgcallbot instance holds the same DATABASE_URL` دیدید، قفل را دور نزنید؛ نمونهٔ مالکِ همان دیتابیس را شناسایی کنید. هنگام بالا آمدن، ۱۰ ثانیه انتظار بعد از قفل طبیعی است.

قبل از فعال‌کردن سفارش‌های بزرگ، اطمینان حاصل کنید نسخهٔ قدیمی یا برنامهٔ مستقل از سشن‌ها استفاده نمی‌کند. برای مشاهدهٔ پردازه‌ها/کانتینرها بدون نمایش سشن‌ها:

```bash
ps -eo pid,lstart,args | grep -E '[p]ython.*main.py|[t]gcallbot'
docker ps --format '{{.Names}} {{.Image}} {{.Status}}'
```

این دستورها **فقط** نمونه‌ها را نشان می‌دهند؛ بی‌هدف پروسه یا کانتینر را `kill` نکنید. قفل جدید نمی‌تواند نسخهٔ قدیمی‌ای را که آن را نمی‌شناسد متوقف کند. از چاپ Session String یا کلید رمزنگاری در لاگ/چت پشتیبانی خودداری کنید.

## بازیابی اکانت‌های آسیب‌دیده

1. همهٔ مصرف‌کنندگان **همان Session String** را شناسایی کنید: ردیف اصلی، کپی‌های نمایندگی، سرور/کانتینر قدیمی و ابزارهای شخص ثالث. برای تشخیص یکسان‌بودن کلید، سشن‌های واقعی را عمومی منتشر نکنید.
2. هر اتصال اضافی را با توقف **کنترل‌شده** ببندید و چند ثانیه برای رفع اتصال قدیمی صبر کنید. در پنل، به‌جای پروب انبوه، فقط یک اکانت را بررسی کنید. اگر در ویس است، بررسی ad-hoc عمداً رد می‌شود؛ این به معنی خروج از سشن نیست.
3. اگر تلگرام `SESSION_REVOKED`/`AUTH_KEY_UNREGISTERED`/`AUTH_KEY_INVALID`/۴۰۱ داد یا پس از رفع قطعی تداخل همچنان کلید غیرقابل استفاده بود، از مسیر «افزودن اکانت» با شماره **دوباره وارد شوید** تا کلید تازه صادر و ذخیره شود. کلید قدیمی را با پاک‌کردن وضعیت DB یا کپی مجدد Session String نمی‌شود تعمیر کرد.
4. برای استفادهٔ هم‌زمان یک اکانت در دو ربات (اصلی/نمایندگی)، در هر ربات جداگانه ورود کنید؛ کپی‌کردن همان سشن مجاز نیست. بعد از اطمینان از اتصال سالم، سفارش‌های کم‌تعداد را آزمایش و تعداد اکانت‌های حاضر را پایش کنید.

آزمون‌های بدون اتصال به تلگرام: `python -m unittest discover -s tests -q`. این آزمون‌ها مسیرهای برنامه را پوشش می‌دهند، اما **سلامت سشن‌های واقعی سرور یا نبودن مصرف‌کنندهٔ شخص ثالث را ثابت نمی‌کنند**.
