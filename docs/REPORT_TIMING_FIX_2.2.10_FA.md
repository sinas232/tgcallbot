# نسخهٔ ۲.۲.۱۰ — گزارش شروع در ابتدای اجرا، نه هنگام پایان

## ایرادهای مشخص‌شده در کد

- جاب زمان‌بندی پس از `submit_order` مستقلاً برای مشتری پیام شروع می‌فرستاد. این تابع فقط تسک اجرا را راه می‌اندازد؛ منتظر پایان آن نیست. بنابراین اجرای سریع یا کندی lookup/ارسال اعلان می‌توانست باعث شود پیام شروع مشتری پس از پیام پایان برسد.
- پیام تأیید پرداخت سفارش فوری نیز پس از راه‌اندازی تسک و مستقل از عمر آن ارسال می‌شد؛ در اجرای سریع امکان جابه‌جایی پیام ثبت و پایان وجود داشت.
- گزارش کانال در نسخهٔ ۲.۲.۹ از قبل در ابتدای executor و با `await` ارسال می‌شد، نه در انتهای آن. اما lookup تعداد اکانت‌ها جلوتر از گزارش بود، ارسال مهلت کلی نداشت و زمان نمایش‌داده‌شده از زمان پولی یا زمان ثبت گرفته می‌شد. این خصوصاً برای رزرو، زمان شروع عملیات را نادرست نشان می‌داد.

این‌ها یافته‌های کد و تست بازتولید رقابت‌اند؛ بدون نسخه و لاگ سرور نمی‌توان علت دقیق رخداد گزارش‌شده در محیط واقعی را قطعی دانست.

## رفتار اصلاح‌شده

1. تأیید پرداخت سفارش فوری قبل از راه‌اندازی تسک اجرا انجام می‌شود؛ انتظار آن حداکثر ۵ ثانیه است. خطای ارسال، پرداخت موفق را برنمی‌گرداند و تأیید پرداخت برای بعد از پایان صف نمی‌شود.
2. خودِ worker در ابتدای اجرا، پیش از lookup اکانت‌ها و هر عملیات ورود، گزارش کانال «سفارش جدید — شروع اجرا» را ارسال می‌کند. برای سفارش زمان‌بندی‌شده، اعلان شروع مشتری هم در همین مرحله انجام می‌شود؛ جاب دیگر پیام شروع مستقل نمی‌فرستد.
3. ورود اکانت‌ها فقط بعد از پایان تلاش‌های اعلان شروع آغاز می‌شود. تایمر پولی در این انتظار و مرحلهٔ ساخت فعال نیست؛ رفتار مالی نسخهٔ ۲.۲.۹ حفظ شده است.
4. پیام رزرو به‌صراحت ثبت رزرو است، نه آغاز اجرا. زمان آغاز عملیات از رخداد واقعی ابتدای worker گرفته می‌شود؛ `started_at` مالی تغییر معنا نداده است. سفارش حجمی همچنان بر اساس ورودهای موفق محاسبه می‌شود.
5. هر تلاش گزارش کانال/شروع زمان‌بندی‌شده مهلت ۸ ثانیه دارد؛ ثبت نتیجهٔ خطا حداکثر ۲ ثانیه اضافه فرصت دارد. ارسال کند برای پایان سفارش رها یا صف نمی‌شود. خطای گزارش اجرای سفارش را لغو نمی‌کند.
6. قفل سبک به‌ازای سفارش تلاش‌های گزارش را مرتب می‌کند؛ قفل‌های تمام‌شده در حافظه باقی نمی‌مانند. وضعیت سفارش بعد از claim و قبل از RPC شروع/رزرو دوباره بررسی می‌شود؛ fallback قالب هم همین بررسی را دارد.
7. claim پایدار اعلان شروع مشتری اضافه شده؛ claimهای کانال و کلید مشترک گزارش نهایی حفظ شده‌اند. اعلان شروع برای سفارش نهایی‌شده رد می‌شود. نتیجهٔ ارسال مبهم `uncertain` است و دوباره ارسال نمی‌شود.
8. گزارش پایان فقط پس از انتقال معتبر به وضعیت نهایی است. لغو حین ارسال شروع، آن تلاش را متوقف می‌کند و گزارش نهایی بعد از آن انجام می‌شود؛ مصرف و عودت همچنان از تسویهٔ اتمیک قبلی به دست می‌آیند.

## مرز تضمین

تلگرام تضمین exactly-once یا تحویل قابل‌اثبات پس از timeout ندارد. اگر درخواست به سرور تلگرام رسیده ولی پاسخ گم شده باشد، لغو coroutine تضمین نمی‌کند خود تلگرام پیام را دیرتر تحویل ندهد. برای جلوگیری از تکرار، چنین پیامی خودکار resend نمی‌شود؛ ممکن است یک اعلان گم شود. این نسخه ترتیب تلاش‌های برنامه و عدم ایجاد شروع معوق/تکراری را کنترل می‌کند، نه شبکهٔ بیرونی را. در نبود تنظیم کانال یا دسترسی ربات، گزارش کانال قابل تحویل نیست.

لاگ‌ها اکنون آغاز اجرا و ارسال موفق گزارش را با شناسهٔ سفارش ثبت می‌کنند:

```text
Order ...: execution starting; reporting before build (bot=...)
Order ...: report sent kind=started audience=channel
Order ...: report sent kind=started audience=customer
Order ...: report sent kind=completed audience=channel
```

## بررسی

۱۵ تست جدید: ۱۳ تست ترتیب/زمان‌بندی و ۲ تست PostgreSQL واقعی برای لغو حین ارسال شروع کانال و مشتری. موارد شامل سفارش فوری و زمان‌بندی‌شدهٔ حجمی، ویس زمان‌دار، ارسال کند، timeout، لغو، عدم replay، رد ارسال پس از تغییر وضعیت، fallback قالب، تقدم تأیید پرداخت، زمان نمایش و آزادشدن قفل‌هاست.

مجموع: **۳۱۷ تست موفق بدون skip، شامل ۲۹ تست PostgreSQL واقعی**؛ compileall و `git diff --check` نیز اجرا شدند. API تلگرام در تست‌ها mock است؛ تست زنده روی سرور مشتری انجام نشده است.

## نصب امن

قیمت‌گذاری، محاسبهٔ عودت، امکانات پریمیوم/نمایندگی و حذف سقف CPU/RAM حفظ شده‌اند. migration جدیدی لازم نیست.

ابتدا حالت تعمیرات را فعال کنید و اجازه دهید سفارش‌های پولی فعال تمام شوند. سپس از دیتابیس و فایل‌های محیط بکاپ بگیرید. بازیابی اتصال پس از restart هنوز پیاده‌سازی نشده؛ سفارش قطع‌شده تسویه می‌شود، نه اینکه اتصالش خودکار ادامه یابد.

در مسیر واقعی پروژه، پس از اطمینان از نبود تغییر محلی ناسازگار:

```bash
git status --short
git fetch origin
git switch arena/01a0b5c9-tgcallbot
git pull --ff-only origin arena/01a0b5c9-tgcallbot
docker compose up -d --build --no-deps bot
docker compose logs --tail=120 bot
```

اگر هر دستور شکست خورد، ادامه ندهید. فایل `.env` و volumes را نگه دارید؛ از `down -v`، `reset --hard` یا restart مخرب استفاده نکنید. نسخهٔ ۲.۲.۱۰ را در لاگ آغاز بررسی کنید؛ سپس تعمیرات را خاموش کنید و با یک سفارش کوچک ترتیب شروع/ورود/پایان را کنترل کنید.
