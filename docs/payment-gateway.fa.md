# 💳 راه‌اندازی کامل درگاه پرداخت زرین‌پال

این سند همه‌چیزِ لازم برای راه‌اندازی درست درگاه پرداخت آنلاین (زرین‌پال) را
پوشش می‌دهد: از تنظیم دامنه و DNS گرفته تا الزام «تطابق دامنهٔ» شاپرک، جریان
فنی پرداخت در این ربات، و عیب‌یابی گام‌به‌گام. **برای به‌روزرسانی نسخه روی
سرور دارای سفارش، فقط [دستورهای نهایی استقرار](deploy-final.fa.md) معتبرند.**

> **خلاصهٔ یک‌خطی مشکل رایج:** اگر «بعد از پرداخت موفق، کیف پول شارژ نمی‌شود»
> یا «کاربر به ربات برنمی‌گردد»، تقریباً همیشه علتش یکی از این سه‌تاست:
> (۱) `SERVER_URL` اشتباه، (۲) `ZARINPAL_MERCHANT` خالی، (۳) پرداخت مستقیم از
> بات بدون صفحهٔ میانی (نقض الزام Referrer شاپرک). هر سه در ادامه حل می‌شوند.

---

## ۱) مفاهیم پایه — دو چیز که نباید اشتباه گرفته شوند

خیلی‌ها این دو را قاطی می‌کنند و همین باعث خرابیِ پرداخت می‌شود:

### الف) «زیردامنهٔ اختصاصی زرین‌پال» (اختیاری، فقط برای زیبایی)
در پنل زرین‌پال، بخش «تنظیمات فنی»، می‌توانید یک زیردامنه مثل
`payment.example.com` تعریف کنید که با یک رکورد **CNAME → `zpc.zarinpal.com`**
به **سرورِ خودِ زرین‌پال** اشاره می‌کند. این فقط باعث می‌شود صفحاتِ پرداختِ
خودِ زرین‌پال زیر برند شما نمایش داده شوند.

- ✅ این به سرورِ **زرین‌پال** اشاره می‌کند، نه سرور شما.
- ❌ **نباید** `SERVER_URL` را روی این آدرس بگذارید.
- برای ربات API-محور، این قابلیت الزامی نیست.

### ب) «آدرس callback ربات» (الزامی)
این آدرسِ وب‌سرورِ **خودِ شما** (همان VPS که ربات روی آن اجراست) است که کاربر
بعد از پرداخت به آن برمی‌گردد و ربات کیف پول را شارژ می‌کند. این همان
`SERVER_URL` در فایل `.env` است و **باید به سرور خودتان** اشاره کند.

| ویژگی | زیردامنهٔ اختصاصی زرین‌پال | آدرس callback (`SERVER_URL`) |
|---|---|---|
| رکورد DNS | `CNAME → zpc.zarinpal.com` | `A → IP سرور شما` |
| اشاره می‌کند به | سرور زرین‌پال | سرور خودتان (VPS) |
| الزامی؟ | خیر (اختیاری) | **بله** |
| نمونه | `payment.liontm.ir` | `bot.liontm.ir` |

> 💡 **توصیه:** برای این دو از **دو زیردامنهٔ جدا** استفاده کنید تا با هم تداخل
> نکنند. مثلاً `payment.liontm.ir` برای زیردامنهٔ اختصاصی زرین‌پال، و
> `bot.liontm.ir` برای callback ربات.

## ۲) الزام «تطابق دامنه» شاپرک (بسیار مهم برای بات‌ها)

طبق [مستند رسمی زرین‌پال](https://www.zarinpal.com/blog/الزام-تطابق-دامنه-در-فرآیند-پرداخت/)،
در هر پرداخت **سه نشانی** وجود دارد که باید همگی با دامنهٔ رسمیِ ثبت‌شده در پنل
زرین‌پال تطابق داشته باشند:

1. **آغازگر / ارجاع‌دهنده (Referrer):** صفحه‌ای که کاربر پرداخت را از آن شروع می‌کند.
2. **نتیجهٔ پرداخت (Callback):** صفحه‌ای که کاربر بعد از پرداخت به آن برمی‌گردد.
3. **دامنهٔ رسمی درگاه:** دامنه‌ای که در پنل زرین‌پال/شاپرک ثبت کرده‌اید.

### مشکلِ خاصِ بات‌ها
اگر ربات کاربر را **مستقیم** به `startpay.zarinpal.com` بفرستد، مرورگر
«ارجاع‌دهنده» را خالی (`/`) می‌فرستد، و شاپرک تراکنش را **مردود** می‌کند —
حتی اگر callback درست باشد.

### راه‌حلی که در این ربات پیاده شده
ربات دیگر مستقیم به درگاه لینک نمی‌دهد. به‌جای آن یک **صفحهٔ میانی (فاکتور)**
روی دامنهٔ خودتان می‌سازد و کاربر را ابتدا به آن می‌فرستد:

</div>

```
دکمهٔ «ورود به درگاه» در ربات
        │
        ▼
https://SERVER_URL/pay/{trans_id}        ← صفحهٔ فاکتور روی دامنهٔ شما
        │  (نمایش مبلغ + ریدایرکت خودکار)
        ▼
https://payment.zarinpal.com/pg/StartPay/{authority}   ← درگاه واقعی
        │  Referrer اکنون = دامنهٔ شما ✅
        ▼  (کاربر پرداخت می‌کند)
https://SERVER_URL/payment/callback/zarinpal?Authority=..&Status=OK   ← callback ✅
        │
        ▼
تأیید تراکنش (verify) → شارژ کیف پول
```

<div dir="rtl">

چون صفحهٔ `/pay/{trans_id}` روی دامنهٔ `SERVER_URL` بارگذاری می‌شود، مرورگر
هنگام رفتن به درگاه همین دامنه را به‌عنوان Referrer می‌فرستد. در نتیجه هر سه
نشانی (آغازگر، callback، و دامنهٔ رسمی) روی دامنهٔ شما منطبق می‌شوند و شاپرک
راضی است.

## ۳) پیش‌نیازها

1. **درگاه فعال در زرین‌پال:** یک دامنهٔ اصلی (مثلاً `liontm.ir`) در پنل
   زرین‌پال ثبت و تأیید شده باشد.
2. **شناسهٔ پذیرنده (merchant_id):** از پنل زرین‌پال دریافت کنید.
3. **سرور با IP عمومی:** همان VPS که ربات را اجرا می‌کند.
4. **دسترسی به DNS دامنه:** (مثلاً Cloudflare) برای ساخت رکورد.

## ۴) گام‌به‌گام تنظیم

### گام ۱ — رکورد DNS برای callback بسازید
در پنل DNS خود (مثلاً Cloudflare) یک رکورد **A** بسازید که یک زیردامنه را به
IP سرور شما ببرد:

</div>

```
Type:    A
Name:    bot                         →  یعنی bot.liontm.ir
Content: <IP عمومی سرور VPS شما>
Proxy:   DNS only  (در Cloudflare ابرِ خاکستری، نه نارنجی)
TTL:     Auto
```

<div dir="rtl">

> ⚠️ اگر قبلاً `payment.liontm.ir` را با CNAME به `zpc.zarinpal.com` ساخته‌اید،
> آن را **دست نزنید** — آن برای زیردامنهٔ اختصاصی زرین‌پال است. برای callback از
> اسم دیگری مثل `bot.liontm.ir` استفاده کنید. طبق الزام شاپرک، کافی است این
> زیردامنه زیرمجموعهٔ همان دامنهٔ اصلیِ ثبت‌شده باشد (که هست).

> 🔒 **دربارهٔ Cloudflare Proxy:** اگر پورت `8080` را مستقیم استفاده می‌کنید،
> حالت proxy (ابر نارنجی) کار نمی‌کند چون Cloudflare فقط پورت‌های استاندارد
> (80/443) را پروکسی می‌کند. یا `DNS only` بگذارید، یا (توصیه‌شده) از HTTPS
> روی پورت 443 با nginx استفاده کنید (بخش ۷).

### گام ۲ — merchant_id را در پنل زرین‌پال بگیرید
از میز کار زرین‌پال، شناسهٔ پذیرندهٔ درگاه خود را کپی کنید (فرمتی شبیه
`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`).

### گام ۳ — فایل `.env` را تنظیم کنید

</div>

```bash
# ═══ Web Server & Payment Gateway ═══

# آدرس عمومیِ callback ربات — باید به سرور خودتان اشاره کند و از اینترنت
# قابل‌دسترس باشد. با HTTPS توصیه می‌شود.
SERVER_URL=https://bot.liontm.ir
# یا برای تست سریع بدون HTTPS (اگر پورت 8080 روی فایروال باز باشد):
# SERVER_URL=http://bot.liontm.ir:8080

PORT=8080

# شناسهٔ پذیرندهٔ واقعی زرین‌پال (بدون این، لینک پرداخت ساخته نمی‌شود)
ZARINPAL_MERCHANT=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx

# درگاه آقای پرداخت (در صورت استفاده)
AQAYE_PARDAKHT_PIN=sandbox
```

## ۶) جریان فنی پرداخت (برای توسعه‌دهنده)

| مرحله | کجا | چه اتفاقی می‌افتد |
|---|---|---|
| ۱. کاربر مبلغ را وارد می‌کند | `handlers/wallet_handlers.py` | `handle_charge_amount` مبلغ (تومان) را می‌گیرد |
| ۲. ساخت لینک | `services/payment_service.py` | `create_payment_link`: زرین‌پال authority می‌دهد؛ لینک واقعی در `pay_url` دیتابیس ذخیره می‌شود؛ آدرس صفحهٔ میانی به کاربر داده می‌شود |
| ۳. صفحهٔ میانی | `main.py → pay_redirect_handler` | `/pay/{trans_id}` فاکتور را نشان می‌دهد و به درگاه ریدایرکت می‌کند |
| ۴. پرداخت | زرین‌پال | کاربر پرداخت می‌کند |
| ۵. بازگشت | `main.py → zp_callback_handler` | `/payment/callback/zarinpal?Authority=..&Status=OK` |
| ۶. تأیید | `payment_service.verify_payment` | verify با مبلغ به ریال؛ کد 100/101 = موفق |
| ۷. شارژ | `database.update_user_credit` | کیف پول شارژ و تراکنش `paid` می‌شود |

### نکات فنی مهم
- **واحد مبلغ:** کاربر تومان وارد می‌کند و در دیتابیس تومان ذخیره می‌شود.
  تبدیل به ریال (`× ۱۰`) فقط **یک‌بار** در لایهٔ gateway انجام می‌شود.
  (باگ قدیمیِ ضرب دوبارهٔ مبلبغ که verify را با خطای «مغایرت مبلغ» می‌شکست،
  اصلاح شده است.)
- **حداقل مبلغ:** زرین‌پال حداقل ۱۰٬۰۰۰ ریال (۱٬۰۰۰ تومان) را می‌پذیرد.
- **کد نتیجهٔ verify:** `100` = موفق، `101` = قبلاً تأیید شده (هر دو موفق تلقی
  می‌شوند و از شارژ دوباره جلوگیری می‌شود چون وضعیت تراکنش بررسی می‌شود).
- **پارامترهای بازگشت:** زرین‌پال با متد **GET** برمی‌گردد و
  `Authority` + `Status` (`OK`/`NOK`) را در query می‌گذارد.

### درگاه آقای پرداخت (API V2)

این درگاه با مستندات رسمی `panel.aqayepardakht.ir/api/v2` هماهنگ شده است:

- **واحد مبلغ = تومان.** آقای پرداخت مبلغ را به **تومان** می‌گیرد (بین ۱٬۰۰۰ تا
  ۴۰۰٬۰۰۰٬۰۰۰). چون مبلغ داخلیِ ما هم تومان است، **هیچ تبدیلی** انجام نمی‌شود
  (برخلاف زرین‌پال که `× ۱۰` به ریال می‌شود). ضرب اشتباهِ قبلی در ۱۰ حذف شد.
- **پارامترهای create:** `pin` (کد پین درگاه — نه `key`)، `amount` (تومان)،
  `callback` (نه `callback_url`)، `callback_method=GET`، به‌همراه
  `invoice_id`/`mobile`/`email`/`description`. با `Content-Type: form` (POST body)
  ارسال می‌شود.
- **لینک پرداخت:** پاسخِ create فقط `transid` می‌دهد؛ لینک را خودمان می‌سازیم:
  - واقعی: `https://panel.aqayepardakht.ir/startpay/{transid}`
  - سندباکس (وقتی `pin=sandbox`): `https://panel.aqayepardakht.ir/startpay/sandbox/{transid}`
- **بازگشت (callback):** چون `callback_method=GET` است، آقای پرداخت با متد **GET**
  برمی‌گردد و `transid`, `status` (۱=موفق/۰=ناموفق), `cardnumber`,
  `tracking_number`, `bank`, `invoice_id` را می‌فرستد. هندلر هم GET و هم POST را
  می‌پذیرد.
- **verify:** پارامترهای `pin` + `transid` + `amount` (تومان). کد `1` = موفق و
  کد `2` = «قبلاً وریفای و پرداخت شده» — **هر دو موفق** تلقی می‌شوند (کد ۲ دیگر
  به‌اشتباه ناموفق ثبت نمی‌شود). شمارهٔ کارت و شمارهٔ پیگیری از خودِ callback به
  گزارش منتقل می‌شوند.
- **تنظیم PIN:** در پنل ادمین ربات، بخش درگاه‌ها، «تنظیم PIN» را با کد پین درگاهتان
  پر کنید. برای تست، مقدار `sandbox` را بگذارید.
- **الزام هم‌دامنه بودن:** آدرس `callback` باید با دامنهٔ درگاهِ تاییدشده در آقای
  پرداخت روی **یک دامنه** باشد؛ در غیر این‌صورت خطای `-15` می‌گیرید. صفحهٔ میانیِ
  `/pay/{trans_id}` این تطابق Referrer را تضمین می‌کند.

## ۷) (توصیه‌شده) HTTPS با nginx

بسیاری از مرورگرها و درگاه‌ها با `http://...:8080` هنگام بازگشت مشکل دارند.
بهتر است پشتِ nginx با گواهی رایگان Let's Encrypt، روی پورت 443 قرار دهید:

</div>

```nginx
# /etc/nginx/sites-available/bot.liontm.ir
server {
    listen 80;
    server_name bot.liontm.ir;
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

```bash
# فعال‌سازی + گواهی HTTPS
ln -s /etc/nginx/sites-available/bot.liontm.ir /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx
apt-get install -y certbot python3-certbot-nginx
certbot --nginx -d bot.liontm.ir
```

<div dir="rtl">

سپس در `.env`:

</div>

```bash
SERVER_URL=https://bot.liontm.ir
```

<div dir="rtl">

> نکته: در حالت nginx، پورت `8080` فقط روی `127.0.0.1` لازم است و نیازی به باز
> کردنش روی فایروال عمومی نیست.

## ۸) عیب‌یابی (Troubleshooting)

### ❌ «بعد از پرداخت، کاربر به ربات برنمی‌گردد / کیف پول شارژ نمی‌شود»

</div>

```bash
# لاگ ساخت لینک و callback را ببینید
docker compose logs -f bot | grep -iE "ZarinPal create|callback|merchant|SERVER_URL"
```

<div dir="rtl">

عوامل محتمل به‌ترتیب شیوع:

| نشانه در لاگ | علت | راه‌حل |
|---|---|---|
| `callback_url=http://localhost...` | `SERVER_URL` تنظیم نشده | `SERVER_URL` را در `.env` درست کنید |
| هشدار `ZARINPAL_MERCHANT تنظیم نشده` | merchant_id خالی | merchant_id واقعی را وارد کنید |
| `/health` باز نمی‌شود | سرور از اینترنت دیده نمی‌شود | DNS/فایروال/پورت را بررسی کنید |
| `ZarinPal Verify Failed. Code: -33` | مغایرت مبلغ | (رفع شده) مطمئن شوید آخرین کد را pull کرده‌اید |
| تراکنش رد می‌شود ولی مبلغ کم شده | نقض الزام Referrer شاپرک | (رفع شده) صفحهٔ میانی `/pay` فعال است |

### ❌ `/health` باز نمی‌شود

</div>

```bash
# ۱) آیا دامنه به IP درست اشاره می‌کند؟
nslookup bot.liontm.ir        # باید IP سرور شما را نشان دهد

# ۲) آیا پورت روی فایروال باز است؟ (اگر بدون nginx و مستقیم 8080)
sudo ufw allow 8080/tcp

# ۳) آیا وب‌سرور داخل کانتینر بالاست؟
docker compose logs bot | grep "Web Server running"

# ۴) تست محلی روی خود سرور
curl -s http://127.0.0.1:8080/health
```

<div dir="rtl">

> یادآوری: چون ربات با `network_mode: service:warp` اجرا می‌شود، پورت `8080`
> از روی کانتینر **warp** منتشر می‌شود (نه bot). این در `docker-compose.yml`
> از قبل درست تنظیم شده است.

### ❌ `ZarinPal Connection Error` (پیام خالی) ~۱۵ ثانیه بعد از «create»

اگر در لاگ دیدید:
```
ZarinPal create: ... callback_url=http://pay.example.com:8080/...
[۱۵ ثانیه بعد]
ZarinPal Connection Error:
```
این یعنی **خودِ ربات نمی‌تواند به `payment.zarinpal.com` وصل شود** (timeout).

**علت:** ربات با `network_mode: service:warp` اجرا می‌شود، پس کل ترافیکش از
IP خارجیِ WARP می‌رود. اما زرین‌پال (و آقای پرداخت) سرویس‌های **ایرانی**‌اند و
اتصال از IP خارجی را **مسدود** می‌کنند.

**راه‌حل (از قبل در پروژه پیاده شده):** یک کانتینر پروکسیِ سبک به نام
`payproxy` اضافه شده که روی شبکهٔ عادیِ داکر (بدون WARP) است و ترافیکش از IP
ایرانیِ هاست خارج می‌شود. ربات فقط درخواست‌های پرداخت را از این پروکسی رد
می‌کند؛ تماس‌های صوتی همچنان از WARP می‌روند.

- در `docker-compose.yml` سرویس `payproxy` تعریف شده و متغیر
  `PAYMENT_HTTP_PROXY=http://payproxy:8888` به ربات داده می‌شود.
- برای فعال‌شدن در نصب موجود، فقط پس از بررسی سفارش‌ها و تهیهٔ بکاپ طبق
  [راهنمای استقرار نهایی](deploy-final.fa.md) نسخهٔ کامل را نصب کنید. build
  مستقیم یا شاخهٔ قدیمی را وسط سفارش پولی اجرا نکنید.
- در لاگ باید ببینید: `... proxy=http://payproxy:8888` (نه `proxy=direct`).
- تست دستیِ سلامت پروکسی از داخل کانتینر ربات:
  ```bash
  docker compose exec bot sh -c "curl -s -m 20 -x http://payproxy:8888 https://payment.zarinpal.com/pg/v4/payment/request.json -o /dev/null -w '%{http_code}\n'"
  ```
  اگر عددی غیر از `000` دیدید (مثلاً `200` یا `422`)، یعنی پروکسی درست کار می‌کند.

> نکته: اگر سرور شما اصلاً IP ایرانی ندارد (کلاً خارج ایران است)، این پروکسی
> هم به زرین‌پال نمی‌رسد. در آن صورت باید ربات را روی سروری با IP ایران اجرا
> کنید، یا از یک درگاه پرداخت که از خارج در دسترس است استفاده کنید.

### ❌ خطای «مغایرت مبلغ» در verify
مطمئن شوید آخرین نسخهٔ کد را دارید (باگ ضرب دوبارهٔ مبلغ رفع شده). مبلغ باید
یک‌بار در لایهٔ gateway به ریال تبدیل شود.

### ❌ تراکنش‌ها بعد از مدتی رد می‌شوند (تعلیق درگاه)
احتمالاً الزام تطابق دامنهٔ شاپرک رعایت نشده. مطمئن شوید:
- کاربر از صفحهٔ میانی `/pay/{trans_id}` عبور می‌کند (مستقیم به درگاه نمی‌رود).
- `SERVER_URL` زیرمجموعهٔ دامنهٔ ثبت‌شده در پنل زرین‌پال است.

### دستور تست دستیِ verify (پیشرفته)
اگر خواستید authority یک تراکنش را دستی تأیید کنید، از لاگ‌ها authority را
بردارید و در دیتابیس وضعیت تراکنش را بررسی کنید:
