# نسخهٔ ۲.۲.۱۴ — محاسبهٔ مصرف بر اساس «زمان فعال سفارش»

این نسخه قاعدهٔ محاسبه را **ساده و قاطع** می‌کند: معیار، زمان فعال بودن خود سفارش است؛ تعداد اکانتی که وارد شده‌اند هیچ تأثیری بر مبلغ ندارد.

## قاعدهٔ نهایی

- **زمان فعال سفارش** = از لحظهٔ آغاز خدمت (پس از ارسال اطلاع‌رسانی شروع) تا لحظهٔ لغو.
- **مصرف = مبلغ پلن × زمان فعال ÷ مدت پلن** و **عودت = مبلغ پلن − مصرف**.
- ورود اکانت‌ها، دیر آماده‌شدن، یا کم‌شدن تعداد آن‌ها مبلغ را تغییر نمی‌دهد؛ فقط minutos فعال مهم است.
- زمان اطلاع‌رسانی شروع، زمان انتظار قبل از شروع خدمت، و هر زمان پس از لغو هزینه ندارد.
- مصرف تا پایان مدت پلن سقف دارد؛ بیش از مدت پلن چیزی اضافه‌گرفته نمی‌شود.
- خدمات بدون مدت (مثل عضویت گروهی بدون زمان) مثل قبل بر اساس تعداد ورود موفق محاسبه می‌شوند.

## نمونهٔ عددی

پلن ۳۰۰٫۰۰۰ تومان، ۱۲۰ دقیقه؛ سفارش ۲۴ دقیقه فعال بوده و بعد لغو شده:

| مورد | مقدار |
|---|---|
| زمان فعال سفارش | ۲۴ دقیقه = ۱٬۴۴۰ ثانیه |
| نسبت به مدت پلن | 1440 ÷ 7200 = ۲۰٪ |
| مبلغ مصرف‌شده | ۶۰٬۰۰۰ تومان |
| مبلغ عودت | ۲۴۰٬۰۰۰ تومان |

اگر ۲ دقیقه فعال بوده باشد: مصرف ۵٬۰۰۰ و عودت ۲۹۵٬۰۰۰ تومان. اگر زمان فعال به‌اندازهٔ کل پلن برسد، مصرف کامل و عودت صفر است.

## دقت محاسبه

- ثانیه‌های کسری با `Decimal` نگه داشته می‌شوند و مبلغ **یک‌بار** در تسویه به دو رقم گرد می‌شود؛ جمع مصرف و عودت دقیقاً برابر مبلغ پلن است.
- زمان فعال در جدول `order_billings` هر ۵ ثانیه ذخیره می‌شود؛ پس از ری‌استارت، همان مقدار ثبتی مبناست و زمان توقف دوباره محاسبه نمی‌شود.
- در ذخیره‌سازی فقط ثانیهٔ کامل ثبت می‌شود؛ کسریِ کمتر از یک ثانیه به‌سود کاربر بخشیده می‌شود تا لغو سریع باعث کسر یک‌صدم تومانی نشود.
- اگر ذخیره‌سازی قطع شود، تیکر در حافظه ادامه می‌یابد، ولی بعد از توقف ناگهانی فقط تا آخرین نقطهٔ ثبتی معتبر است (بخشش به کاربر، نه ادعای مالی نامطمئن).
- `started_at` هنگام آغاز خدمت ثبت می‌شود اما مبنای پول، مقدار ثبتی تیکر است، نه محاسبهٔ دوبارهٔ ساعت.

## تغییرات گزارش‌ها

- گزارش لغو: ردیف **«زمان فعال سفارش (مبنای محاسبه)»** و خط **«مبنا: زمان فعال سفارش از آغاز خدمت تا لغو، نسبت به مدت پلن»**.
- پیام شروع اجرا: «زمان فعال سفارش نسبت به مدت پلن محاسبه می‌شود؛ در لغو فقط زمان فعال کسر و ماندهٔ مصرف‌نشده عودت می‌شود.»
- پیش‌نمایش پرداخت: همان قاعده برای سفارش‌های زمان‌دار و مدت‌دار.
- پاسخ لغو به کاربر: «زمان فعال سفارش (مبنای محاسبه)» و «زمان باقی‌مانده از پلن».
- گزارش‌ها همچنان از یک رسید مالی واحد خوانده می‌شوند؛ لغو هم‌زمان چندباره فقط یک عودت می‌دهد.

## تفاوت با ۲.۲.۱۳

نسخهٔ ۲.۲.۱۳ مصرف را به حضور تأییدشدهٔ هر اکانت گره زده بود (۲۵ اکانت از ۵۰ اکانت = نصف نرخ). آن قاعده کنار گذاشته شد. نسخهٔ ۲.۲.۱۳ هرگز روی سرور شما نصب نشد و رسیدهای تسویهٔ قبلی بازمحاسبه نمی‌شوند؛ اصلاح برای تمام لغوهای بعد از نصب این نسخه اعمال می‌شود.

## تست‌ها

**۳۷۴ تست موفق بدون skip، شامل ۳۵ تست PostgreSQL واقعی.** تست‌های جدید این نسخه:

- ۲۴ دقیقه فعال از پلن ۱۲۰ دقیقه و ۳۰۰٬۰۰۰ تومان ⇒ مصرف ۶۰٬۰۰۰ و عودت ۲۴۰٬۰۰۰ تومان.
- مبلغ با ۰، ۱، ۲۵ و ۵۰ اکانت حاضر یکسان است.
- زمان انتظار پیش از آغاز خدمت و زمان پس از لغو هزینه ندارد.
- مصرف از مدت پلن بیشتر نمی‌شود.
- اجرای واقعی executor در PostgreSQL: لغو در میانهٔ ساخت، تسویه با اعداد بالا، کیف پول ۴۴۰٬۰۰۰، رسید با `billing_basis=active_time` و ترتیب گزارش شروع→لغو.
- ۲۰ تسویهٔ هم‌زمان ⇒ فقط یک عودت.
- ری‌استارت: تسویه از checkpoint، بدون عودت دوباره.
- خدمات بدون مدت همچنان بر اساس تعداد ورود موفق محاسبه می‌شوند.
- قطعی ذخیره‌سازی، تیکر را متوقف نمی‌کند و پیام «۰ ثانیه» اشتباه تولید نمی‌شود.

تست‌ها با API ماک‌شده اجرا شده‌اند؛ ویس‌کال و تلگرام واقعی آزمایش نشده و روی سرور شما نصب نشده است.

## دستورات نصب امن

ابتدا تعمیرات را روشن کنید، سفارش‌های فعال را تمام کنید و بکاپ بگیرید:

```bash
(
set -e
umask 077
mkdir -p backups
stamp=$(date +%Y%m%d-%H%M%S)
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "backups/before-2.2.14-$stamp.dump"
test -s "backups/before-2.2.14-$stamp.dump"
if [ -f .env ]; then cp -p .env "backups/env-before-2.2.14-$stamp"; fi
)
```

سپس نصب:

```bash
(
set -e
if [ -n "$(git status --porcelain)" ]; then
  echo 'Local changes exist; preserve and review them before updating.'
  exit 1
fi
git fetch origin
git switch arena/01a0b5c9-tgcallbot
git pull --ff-only origin arena/01a0b5c9-tgcallbot
docker compose up -d --build --no-deps bot
docker compose logs --tail=120 bot
)
```

نسخهٔ **2.2.14** را در لاگ/پنل بررسی کنید. بعد از نصب، یک سفارش آزمایشی کوتاه بگیرید، چند دقیقه صبر کنید و لغو کنید تا مبلغ مصرف و عودت را در گزارش ببینید.

## محدودیت‌ها

- زمان فعال با ساعت داخلی سرور اندازه‌گیری می‌شود؛ جابه‌جایی ساعت سیستم روی تیکر در حافظه اثر ندارد، ولی اختلاف ساعت نمایشی گزارش‌ها ممکن است.
- اتصال فعال ویس پس از ری‌استارت از سر گرفته نمی‌شود؛ سفارش قطع‌شده از روی checkpoint تسویه می‌شود.
- اگر ذخیره‌سازی مدت‌ها قطع بماند و ربات هم ناگهانی متوقف شود، بخشی از زمان فعال از دست می‌رود و به‌نفع کاربر نادیده گرفته می‌شود.
