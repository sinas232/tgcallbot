# پنج سفارش موازی

محدودیت قدیمی `if self.active_orders` حذف شده است. اجرای سفارش‌ها اکنون مانند پذیرش خرید، از `MAX_CONCURRENT_ORDERS` استفاده می‌کند. برای سقف پنج سفارش، مقدار آن را در `.env` برابر 5 قرار دهید. مقدار قدیمی/تکراری این متغیر را باقی نگذارید.

اشتراک اکانت بین گروه‌های متفاوت به صورت opt-in:

```
MAX_CONCURRENT_ORDERS=5
VOICE_SHARE_ACCOUNTS_ACROSS_ORDERS=true
```

در این حالت، انتخاب اکانت به دلیل داشتن سفارش دیگر رد نمی‌شود. فقط یک Pyrogram client و یک PyTgCalls engine برای هر اکانت وجود دارد؛ اتصال‌های native به تفکیک chat و وضعیت سفارش به تفکیک (order, account) نگهداری می‌شوند. هیچ session جدیدی برای هر سفارش ایجاد نمی‌شود. خاتمهٔ یک سفارش تنها leave همان chat را اجرا می‌کند؛ teardown کلاینت حتی با force، در حضور سفارش دیگر یا reservation/join درحال اجرا متوقف می‌شود.

حالت پیش‌فرض false برای استقرارهای قبلی حفظ شده است؛ در این حالت سفارش‌های موازی به اکانت‌های مجزا نیاز دارند. محافظ rebuild موتور مشترک، FloodWait، فریز اکانت و مالکیت سشن حذف نشده‌اند. هم‌زمانی سفارش‌ها با ارسال بی‌محدودیت Join تفاوت دارد.

تست‌های آفلاین: پذیرش هم‌زمان پنج worker و رد ششم، حفظ مالکیت سشن هنگام اشتراک، خروج از یک chat بدون خروج از chat دیگر، جلوگیری از teardown با رزرو سفارش دیگر. تست واقعی پنج گروه با اکانت‌های سرور انجام نشده است؛ موفقیت تست‌های آفلاین تضمین اتصال/مدیای Telegram نیست. ابتدا یک اکانت آزمایشی را در دو گروه غیرتولیدی بررسی کنید و خروج از یکی و باقی‌ماندن در دیگری را در خود Telegram نیز بسنجید، سپس پنج سفارش را آزمایش کنید.

برای نصب، تا پایان سفارش فعال صبر کنید و از دستور fetch/merge --ff-only و build استفاده کنید. تغییر env فقط با recreate کانتینر اعمال می‌شود؛ حین سفارش فعال recreate نکنید.

تکمیل بعدی: سفارش pending پرداخت‌شده اکنون با job دوره‌ای بازیابی می‌شود؛ شرایط و رفتار سفارش 1001 در docs/pending-paid-orders.fa.md آمده است. هیچ پرداخت یا عودت دوباره‌ای در این job انجام نمی‌شود.
