# اصلاح آمار و تعمیرات — نسخهٔ ۲.۲.۸

مبنای این نسخه همان `7a3f68d` (نسخهٔ ۲.۲.۷) است که در لاگ سرور دیده می‌شد.
بهینه‌سازی CPU، لغو اتمیک، رسید عودت، اجرای موجی و قابلیت‌های قبلی حفظ شده‌اند.

## علت‌ها و اصلاحات

### ۱. دکمهٔ «آمار کل ربات»

`@require_admin` اشتباهاً بالای تابع همگام `_server_resource_line()` قرار داشت،
نه بالای هندلر `bot_stats_handler(update, context)`. در نتیجه فراخوانی تابع کمکی
بدون update/context دقیقاً همان TypeError لاگ را ایجاد می‌کرد.
اکنون کنترل دسترسی روی خود هندلر است. خواندن منابع سیستم هم با `asyncio.to_thread`
انجام می‌شود تا نمونه‌برداری CPU حلقهٔ رویداد و پاسخ‌گویی دکمه‌ها را متوقف نکند.

### ۲. تعمیرات پس از ری‌استارت از کار می‌افتاد

ربات اصلی پیش از `Application.initialize()`، `bot_id` و وضعیت تعمیرات را تنظیم
می‌کرد. initialize فایل pickle را بارگذاری و `bot_data` را جایگزین می‌کند؛ بنابراین
مقدار معتبر دیتابیس با مقدار قدیمی فایل یا حتی bot_data خالی جایگزین می‌شد.
نبودن bot_id در `Error in bot ?` هم با این مسیر سازگار است.

اکنون ترتیب مشترک ربات اصلی و نمایندگی این است:

1. بارگذاری persistence؛
2. تنظیم مجدد هویت درست ربات؛
3. بارگذاری وضعیت تعمیرات از دیتابیس، فقط `bot_id=1`؛
4. سپس شروع پردازش آپدیت‌ها.

نیازی به پاک‌کردن فایل pickle نیست. اگر خواندن وضعیت دیتابیس شکست بخورد، دسترسی
کاربران **بسته** می‌ماند؛ سوپرادمین پس از رفع اتصال باید وضعیت را از پنل دوباره ذخیره کند.
خطای ذخیره نیز پیام موفقیت کاذب نمی‌دهد.

### ۳. پوشش کامل گارد و جلوگیری از خرید همزمان با فعال‌سازی

- گارد در گروه مستقل `-3` تمام Updateها را می‌گیرد: متن، دستور، کال‌بک، عکس،
  فایل، مخاطب و پیام ویرایش‌شده. خراب‌شدن ارسال اعلان باعث عبور کاربر نمی‌شود.
- فقط مدیرهای اصلی `ADMIN_IDS` و کاربر دارای **هر دو** شرط `is_admin=True` و
  `admin_role=super_admin` مستثنا هستند. نقش قدیمیِ سوپرادمین بعد از لغو دسترسی کافی نیست.
- تغییر وضعیت روی همهٔ Applicationهای همین فرایند، حتی نمایندگی در حال راه‌اندازی،
  اعمال می‌شود و فقط یک تنظیم مشترک در دیتابیس نوشته می‌شود.
- قبل از کسر وجه/ثبت سفارش مجدداً وضعیت بررسی می‌شود. بخش نهایی پذیرش و تغییر
  تعمیرات قفل مشترک دارند؛ بررسی ظرفیت یا فرم قدیمی نمی‌تواند این مرز را دور بزند.
- سفارش زمان‌بندی‌شده هنگام تعمیرات شروع نمی‌شود؛ وضعیت رزرو حفظ می‌شود.
- روشن‌کردن تعمیرات به‌خودی‌خود سفارش **از قبل فعال** را لغو نمی‌کند؛ پایان سرویس و
  عملیات مالیِ درحال انجام مسیر قبلی را دارند. ری‌استارت کانتینر همچنان تماس فعال را قطع می‌کند.
- در حالت عادی برای گارد تعمیرات هیچ درخواست دیتابیس به‌ازای هر آپدیت اضافه نشده است.

### ۴. تداخل هندلرهای ربات اصلی با نمایندگی‌ها

رجیستری مکالمه‌ها قبلاً فقط با نام‌هایی مانند `admin` و `support_ticket` کلیدگذاری
می‌شد. ثبت هندلرهای نمایندگی، رجیستری ربات اصلی را جایگزین می‌کرد و پیش‌روتر،
وضعیت مکالمهٔ ربات دیگری را پاک/تنظیم می‌کرد. رجیستری اکنون بر اساس **Application**
جداست. امضای `clear_conversations` نیز با فراخوانی `/start` هماهنگ شده است.

## تست‌ها

۲۰ تست جدید شامل:

- اجرای واقعی PTB initialize با فایل pickle قدیمی و دیتابیس با وضعیت مخالف؛
- روشن/خاموش‌کردن از دکمهٔ dispatcher و اعمال روی ربات اصلی و نمایندگی؛
- جلوگیری از عبور پیام غیرمتنی و کال‌بک قدیمی پرداخت؛
- خطای اعلان، خطای ذخیره و خطای خواندن اولیه؛
- نقش ادمین عادی، سوپرادمین و سوپرادمین لغودسترسی‌شده؛
- فعال‌شدن تعمیرات حین بررسی ظرفیت یا واکشی سفارش‌های رزروی؛
- اجرای کامل دکمهٔ آمار پس از ثبت نمایندگی، با وضعیت قبلیِ ارسال تیکت؛
- ممیزی امضای توابع دارای دکوراتور دسترسی.

مجموع **۲۵۴ تست موفق** در محیط توسعه، شامل تست‌های PostgreSQL نسخهٔ قبلی.
ارتباط تلگرام در تست‌های جدید شبیه‌سازی شده؛ تست پذیرش روی بات زندهٔ شما هنوز لازم است.

## نصب روی سرور شما

ترجیحاً زمانی نصب کنید که سفارش فعال ندارید. `.env`، `data`، فایل‌های pickle و
volumeها را حذف نکنید؛ اسکریپت قدیمی `restart.sh` و `down -v` لازم نیست.

```bash
cd /opt/tgcallbot
set -e

git status --short
# اگر تغییر محلی نشان داده شد، قبل از ادامه آن را بررسی و نگهداری کنید.
git fetch origin arena/01a0b5c9-tgcallbot:refs/remotes/origin/arena/01a0b5c9-tgcallbot
git switch arena/01a0b5c9-tgcallbot
git pull --ff-only origin arena/01a0b5c9-tgcallbot

docker compose up -d --build --no-deps bot
docker compose logs --tail=150 bot
```

در لاگ باید نسخهٔ `2.2.8` و عبارت زیر دیده شود (True/False مطابق وضعیت ذخیره‌شده):

```text
Bot 1: maintenance=True loaded AFTER persistence
```

برای تست محدودِ اصلاحات جدید، بدون اتصال به تلگرام/دیتابیس واقعی:

```bash
docker compose exec -T bot python -m unittest tests.test_maintenance_and_stats -v
```

## تست پذیرش

1. با مدیر اصلی «آمار کل ربات» را بزنید؛ گزارش نهایی باید بعد از پیام انتظار برسد.
2. تعمیرات را روشن کنید. با **یک حساب عادی جدا از ادمین اصلی/سوپرادمین**، `/start`،
   خرید، دکمهٔ پرداخت روی پیام قدیمی و ارسال عکس را امتحان کنید؛ نباید به هندلر عملیاتی برسند.
3. همین را در نمایندگی امتحان کنید.
4. در زمانی که تماس فعال ندارید، کانتینر را ری‌استارت کنید؛ تعمیرات باید همچنان روشن بماند.
5. با سوپرادمین خاموش کنید؛ کاربران باید دوباره به منوها دسترسی داشته باشند.

هشدار تطابق ایموجی پریمیوم یا اعلان انتشار نسخهٔ آزمایشی PyTgCalls علت TypeError
گزارش‌شده نبود. برای این اصلاح، نسخهٔ موتور تماس عوض نشده است.
