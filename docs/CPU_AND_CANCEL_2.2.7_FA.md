# نسخهٔ ۲.۲.۷ — کاهش سربار CPU و لغو امن سفارش

## مبنای تغییرات

این نسخه روی آخرین پوش شاخهٔ معرفی‌شده، یعنی `7a2fc8e` از
`arena/01a0b3b3-tgcallbot` ساخته شده است، نه نسخهٔ قدیمی main.
گارد منابع واقعی نسخهٔ ۲.۲.۶، پذیرش سفارش بزرگ و اجرای موجی، ایموجی پریمیوم،

## علت واقعی دکمهٔ لغو

در PTB فقط اولین هندلر منطبق در **هر گروه** اجرا می‌شود. ضداسپم از نوع
`TypeHandler(Update, ...)` تمام آپدیت‌ها را می‌گرفت؛ نگهبان تعمیرات، لغو و
پیش‌روتر منو که همگی در همان گروه بودند هیچ‌وقت نوبت اجرا پیدا نمی‌کردند.
گروه‌ها اکنون جدا هستند: ضداسپم `-4`، تعمیرات `-3`، لغو `-2` و پیش‌روتر `-1`.
لغو بعد از اجرا انتشار آپدیت را متوقف می‌کند تا مکالمهٔ دیگری آن را دوباره پردازش نکند.

دکمهٔ شیشه‌ای با `callback_data` شناسایی می‌شود، نه تصویر ایموجی.
برای منوهای **Reply** هم نام‌های جایگزین منوهای ثابت از شروع برنامه آماده می‌شوند؛
دکمه‌های قبلی پس از ری‌استارت یا خاموش‌کردن پریمیوم قابل‌شناسایی می‌مانند.

## تسویه و رسید

- قفل ردیف سفارش و کیف پول در PostgreSQL؛ لغو، افزایش موجودی، تراکنش مالی و رسید
  در **یک تراکنش دیتابیس** ثبت می‌شوند. خطا در flush یا commit همه را برمی‌گرداند.
- کلیک مجدد رسید ذخیره‌شده را نشان می‌دهد؛ پول دوباره واریز نمی‌شود.
- سفارش رزروشده/در صف بدون شروع سرویس: عودت کامل.
- سفارش مدتی: `مصرف = ceil(ثانیه‌های سپری‌شده × قیمت ÷ مدت به ثانیه)`،
  حداکثر تا کل قیمت؛ `عودت = قیمت − مصرف`. انتظار و build بدون `started_at` شارژ نمی‌شوند.
- سفارش حجمی: نسبت پیشرفت به تعداد سفارش؛ پیش‌نمایش ادمین و تسویه از یک محاسبه استفاده می‌کنند.
  پیشرفت زندهٔ حجمی در حافظهٔ executor است؛ این نسخه ذخیرهٔ دائمی جدیدی برای پیشرفت حجمی اضافه نمی‌کند.
- رسید شامل کل مبلغ، مصرف، عودت، زمان قابل محاسبه، کد پیگیری و موجودی **پس از تسویه** است.
- اگر پیام قدیمی قابل ویرایش نباشد، رسید در پیام جدید فرستاده می‌شود.
- کاربر فقط سفارش خودش در همان ربات را لغو می‌کند. کال‌بک لغو ادمین نیز نقش ادمین و tenant را بررسی می‌کند.
- سفارش بسته‌شده دیگر توسط submit دوباره اجرا نمی‌شود؛ خروج حساب‌ها همچنان پلکانی است، نه همزمان.
- جدول جدید `order_settlements` هنگام `init_db/create_all` خودکار ساخته می‌شود؛
  جدول یا دادهٔ قدیمی حذف نمی‌شود. رسیدها در بکاپ JSON هم حفظ می‌شوند.

این اصلاح، لغو دستی کاربر/ادمین را اتمیک می‌کند؛ بازپرداخت‌های خودکار ناشی از
ری‌استارت همچنان مسیر جداگانهٔ قبلی خود را دارند. سفارش‌های لغوشدهٔ قدیمی که قبل
از این نسخه رسید نداشته‌اند، خودکار دوباره عودت نمی‌گیرند؛ برای آن‌ها باید دفتر تراکنش بررسی شود.

## CPU: چه چیزی واقعاً اندازه‌گیری شد؟

در کد نصب‌شدهٔ `py-tgcalls==2.3.3`، هر بار `cleanup_commands` یک فرایند
`ffmpeg/ffprobe -h full` اجرا و تمام خروجی آن را parse می‌کند. برای فایل سکوت و
فرمان تکراری، نتیجهٔ همین اعتبارسنجی در یک کش محدود ذخیره می‌شود؛ درخواست‌های
همزمان اعتبارسنجی مشترک دارند. شکست کش نمی‌شود و لغو یک اتصال کش مشترک را نمی‌کشد.
**فریم صوتی، حضور کاربران، شبکه و بررسی سلامت کش نشده‌اند.**

تنظیم قبلی فقط ترد دیکودر را محدود می‌کرد. اکنون تردهای filter و encoder هم
محدودند. فرمت صوتی، حلقهٔ پیوسته، حالت mute و rejoin دست‌نخورده‌اند.

اندازه‌گیری محلی در این محیط، با FFmpeg 7.0.2 و ۵۰ فرمان یکسان:

| معیار | قبل | بعد |
|---|---:|---:|
| تعداد اجرای راهنمای FFmpeg | ۵۰ | ۱ |
| مجموع زمان CPU اعتبارسنجی (فرایند والد + فرزندان) | ۱٫۸۸۶۹ ثانیه | ۰٫۰۳۶۴ ثانیه |
| زمان دیواری اعتبارسنجی | ۱٫۴۵۳۷ ثانیه | ۰٫۰۲۸۱ ثانیه |
| بیشترین ترد فرایند سکوت در آزمایش سه‌ثانیه‌ای | ۸ | ۶ |
| خروجی PCM سکوت در سه ثانیه | ۱۴۴۰۰۰ بایت | ۱۴۴۰۰۰ بایت |

حدود ۹۸٪ کاهش **فقط در سربار اعتبارسنجی تکراری** اندازه‌گیری شد، نه CPU کل ربات.
زمان CPU استریم پایدار در این نمونهٔ کوتاه نزدیک دقت اندازه‌گیری بود؛ از آن
درصد کاهش مصرف پایدار نتیجه نمی‌گیریم. مصرف WebRTC/ntgcalls و شبکهٔ سرور واقعی
در این آزمون حضور ندارند و باید با تعداد تماس یکسان قبل/بعد سنجیده شوند.

سوئیچ بازگشت رفتار کش: `VOICE_FFMPEG_COMMAND_CACHE=false` و ری‌استارت ربات.
پس از تعویض باینری FFmpeg نیز ربات را ری‌استارت کنید. وابستگی اجرایی جدیدی اضافه نشده است.

## به‌روزرسانی امن روی سرور موجود

ابتدا از پنل، تعمیرات را روشن کنید و ترجیحاً صبر کنید سفارش‌های فعال تمام شوند.
ری‌استارت ربات تماس‌های فعال را قطع می‌کند؛ این عملیات را وسط سفارش مهم انجام ندهید.
دستورها را **در همان پوشهٔ استقرار قبلی** اجرا کنید تا نام پروژه و volumeهای Compose عوض نشوند.
اگر Git تغییر محلی گزارش کرد، ابتدا آن را بررسی و نگهداری کنید؛ از `reset --hard` استفاده نکنید.

```bash
cd /path/to/tgcallbot
set -e

git status --short
mkdir -p backups
umask 077
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  > "backups/before-2.2.7-$(date +%Y%m%d-%H%M%S).sql"

git fetch origin arena/01a0b5c9-tgcallbot:refs/remotes/origin/arena/01a0b5c9-tgcallbot
git switch arena/01a0b5c9-tgcallbot
git pull --ff-only origin arena/01a0b5c9-tgcallbot

docker compose up -d --build --no-deps bot
docker compose logs --tail=100 bot
```

سپس نسخهٔ ۲.۲.۷ و سلامت استارت را بررسی کنید و تعمیرات را از پنل خاموش کنید.
فایل `.env`، سشن‌ها و volumeهای قبلی حفظ می‌شوند. **`down -v`، حذف data یا
اسکریپت قدیمی `restart.sh` را برای این به‌روزرسانی اجرا نکنید**؛ آن اسکریپت DNS
و پاکسازی کلی Docker انجام می‌دهد و برای این تغییر لازم نیست.

اگر استقرار شما با `docker-compose.host.yml` است، همان گزینهٔ `-f` قبلی را در
تمام دستورهای Compose استفاده کنید؛ این نسخه نیاز به تغییر مسیر شبکه یا WARP ندارد.

## تست و اندازه‌گیری

```bash
# تست‌های آفلاین؛ بدون توکن و اتصال به تلگرام
# تست‌های PostgreSQL در نبود TEST_DATABASE_URL به‌صراحت skip می‌شوند.
docker compose exec -T bot python -m unittest discover -s tests -v

# بنچمارک محدود FFmpeg (خودش بار کوتاه ایجاد می‌کند؛ زمان خلوت اجرا شود)
docker compose exec -T bot python tools/benchmark_silence_cpu.py --calls 50 --stream-seconds 3

# وضعیت منابع و فرایندها، در بار یکسان قبل و بعد
docker stats --no-stream telegram_bot_container
docker top telegram_bot_container -eo pid,ppid,comm,pcpu,pmem,nlwp
```

برای تست مالی واقعی فقط از **دیتابیس تست جداگانه** استفاده کنید:

```bash
TEST_DATABASE_URL='postgresql+asyncpg://USER:PASSWORD@HOST/TEST_DB' \
  python -m unittest tests.test_settlement_postgres -v
```

تست مالی در schema تصادفی مخصوص خودش اجرا می‌شود و همان schema را پاک می‌کند.
همزمانی ۲۰ لغو، مسابقهٔ پایان/لغو، افزایش همزمان موجودی، rollback زمان insert و commit،
محدودیت مالکیت، لغو بدون عودت و حفظ رسید در backup/restore پوشش داده شده‌اند.
مجموع اجرای این محیط: **۲۳۴ تست موفق**، شامل PostgreSQL واقعی و استریم FFmpeg واقعی.

تست پذیرش تلگرام روی سرور شما هنوز لازم است: سفارش تست رزروی را لغو کنید؛
سفارش مدتی را پس از شروع سرویس لغو کنید؛ مبلغ مصرف + عودت باید برابر کل باشد؛
کلیک دوباره نباید موجودی را افزایش دهد؛ خروج حساب‌ها و گزارش کانال را هم بررسی کنید.
این محیط به بات زنده و بار واقعی سرور شما وصل نشده است.
