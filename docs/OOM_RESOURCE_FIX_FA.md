# رفع سقف منابع پس از OOM تأییدشده — ۲۰۲۶-۰۹-۱۹

## علت این رخداد، نه حدس

لاگ کرنل ارائه‌شده در ساعت `2026-09-19 16:18:50 UTC` (۱۹:۴۸:۵۰ تهران):

```text
memory: usage 1572864kB, limit 1572864kB
constraint=CONSTRAINT_MEMCG
Memory cgroup out of memory: Killed process ... (python)
```

شناسهٔ cgroup با کانتینر ربات یکسان است. Docker در همان ثانیه آن را دوباره
شروع کرده و ساعت `16:19:01 UTC` برنامه نوشته است:

```text
startup recovery: 1 interrupted order(s) queued for refund
```

پس زنجیرهٔ این حادثه: **سقف ۱۵۳۶ MiB → کشتن Python توسط کرنل → restart →
سیاست قدیمی توقف/عودت سفارش**. مقدار فعلی `oom=false` این سابقه را رد نمی‌کند.
این شواهد دلیل کافی برای نسبت‌دادن حادثه به محدودیت CPU، WARP، PEER_ID_INVALID
یا تلاش‌های ورود PostgreSQL نیست. همچنین مشخص نمی‌کند رشد حافظه طبیعی بوده
یا نشت حافظه رخ داده است؛ آن موضوع نیازمند اندازه‌گیری جداگانه است.

## تغییرات این اصلاح

- حذف `deploy.resources.limits` و `mem_limit`/`cpus` از سرویس `bot`.
- هیچ سقف ثابت جایگزینی برای RAM یا CPU تعیین نشده است.
- بهینه‌سازی تک‌ترد ffmpeg، گارد پذیرش سفارش و فاصله‌گذاری درخواست‌های تلگرام
  حفظ شده‌اند؛ این‌ها با سهمیهٔ سخت کانتینر متفاوت‌اند.
- محافظ OOM سیستم‌عامل خاموش نشده است. منابع فیزیکی میزبان/VM و محدودیت‌های
  احتمالی cgroup والد همچنان برقرارند. بدون سقف کانتینری، مصرف بی‌رویه می‌تواند
  کل میزبان را تحت فشار قرار دهد؛ پایش حافظه و CPU ضروری است.

**این اصلاح فقط استقرار/منابع است. ادامهٔ خودکار سفارش پس از restart هنوز
پیاده‌سازی نشده و برنامه همچنان ۲.۲.۸ است. سفارش قبلاً تسویه‌شده را خودکار
به running برنگردانید؛ ممکن است خدمت مجانی یا عودت تکراری ایجاد کند.**

## ۱. دریافت فایل‌ها بدون قطع سفارش

ابتدا تغییرات محلی را بررسی کنید؛ آن‌ها را با reset یا checkout اجباری دور نریزید.
روی شاخهٔ زیر باشید؛ اگر سرور روی شاخهٔ دیگری است، قبل از ادامه بررسی کنید.

```bash
cd /opt/tgcallbot
git status --short
git branch --show-current
git pull --ff-only origin arena/01a0b5c9-tgcallbot
```

دریافت این اصلاح به‌تنهایی کانتینر موجود را تغییر نمی‌دهد؛ `restart.sh`،
`docker compose down` یا `up` وسط سفارش اجرا نکنید.

## ۲. رفع فوریِ سقف زنده بدون restart — اختیاری، فقط cgroup v2

ابزار با Python 3.9+ **روی میزبان Docker** اجرا می‌شود (نه داخل کانتینر).
پیش‌فرض فقط خواندنی است و شناسهٔ کامل کانتینر را با مسیر cgroup پردازش مطابقت
می‌دهد. روی cgroup v1، مسیر ناشناخته، کانتینر متوقف/درحال restart یا نبودن
کنترل‌های موردنیاز خطا می‌دهد و مسیر جایگزین حدسی اجرا نمی‌کند.

ابتدا بررسی:

```bash
sudo python3 tools/unlimit_bot_resources.py
```

اگر مسیر همان کانتینر ربات و مقادیر موردانتظار است، اعمال:

```bash
sudo python3 tools/unlimit_bot_resources.py --apply
sudo python3 tools/unlimit_bot_resources.py
```

خروجی پس از اعمال باید شامل `memory.max: max -> max` و
`cpu.max: max 100000 -> max 100000` باشد (period ممکن است متفاوت باشد).
ابزار فقط کنترل‌های منابع همان cgroup را می‌نویسد؛ هیچ پروسه‌ای را نمی‌کشد،
restart نمی‌کند و به دیتابیس یا وضعیت سفارش‌ها دست نمی‌زند.

**این تغییر زنده موقتی است:** Docker HostConfig عوض نمی‌شود و ممکن است inspect
هنوز سقف قبلی را نشان دهد. با restart/update کانتینر، سقف قبلی ممکن است برگردد.
برای تغییر ماندگار مرحلهٔ بعد لازم است. اگر ابزار خطا داد، خروجی را بررسی کنید؛
تغییرات چند فایل اتمیک نیست و ممکن است بعضی از آن‌ها انجام شده باشند.
این ابزار روی cgroup واقعی سرور شما از این محیط آزمایش نشده است؛ تست‌ها از
فایل‌های موقت و شبیه‌سازی تغییر هویت کانتینر استفاده می‌کنند.

## ۳. اعمال ماندگار — فقط پس از اتمام سفارش‌ها

تعمیرات را روشن کنید تا سفارش جدید پذیرفته نشود؛ منتظر اتمام سفارش‌های جاری
بمانید. تعمیرات به‌تنهایی تماس فعال را حفظ می‌کند، اما restart آن را قطع می‌کند.
زمان مناسب برای رزروهای نزدیک هم در نظر بگیرید.

قبل از بازسازی، تنظیمات مؤثر Compose را بدون چاپ env و اسرار بررسی کنید:

```bash
docker compose config --format json | python3 -c 'import json,sys; b=json.load(sys.stdin)["services"]["bot"]; print({k:b[k] for k in ("mem_limit","mem_reservation","memswap_limit","cpus","cpu_quota","cpu_period","cpuset","deploy") if k in b})'
```

برای Compose مخزن باید `{}` باشد. اگر override محلی هنوز سقف گذاشته، همان را
هم بررسی/حذف کنید؛ فایل نمونه به‌تنهایی override را خنثی نمی‌کند.

پس از تخلیهٔ سفارش‌های فعال:

```bash
docker compose up -d --no-deps --force-recreate bot
docker inspect --format 'Memory={{.HostConfig.Memory}} MemorySwap={{.HostConfig.MemorySwap}} NanoCpus={{.HostConfig.NanoCpus}} CpuQuota={{.HostConfig.CpuQuota}} CpusetCpus={{.HostConfig.CpusetCpus}}' telegram_bot_container
```

`Memory=0` و `NanoCpus=0` یعنی این دو سقف در HostConfig تعیین نشده‌اند؛ CpuQuota
نیز باید صفر/بدون سهمیه و CpusetCpus خالی باشد. این به معنی RAM فیزیکی نامحدود نیست.
دیتابیس/WARP/volumeها را بازسازی یا حذف نکنید؛ نیازی به build مجدد تصویر برای
این تغییر Compose وجود ندارد.

## موارد مستقل باقی‌مانده

- مسیر قدیمی `reset_stuck_orders`/عودت startup باید با checkpoint و ادامهٔ
  باقی‌ماندهٔ خدمت جایگزین شود، با حفظ لغو/تسویهٔ اتمیک؛ این اصلاح آن را انجام نمی‌دهد.
- `coroutine '_notify_user_of_refund' was never awaited` یک باگ اعلان پس از
  restart است؛ علت OOM نیست و در این اصلاح منابع تغییر نکرده است.
- خطای `PEER_ID_INVALID` ارسالی از parsing پیام/Story در dispatcher است؛ با
  خطای ورود به ویس یکی نیست. غیرفعال‌کردن تمام raw updateها اتصال ویس را خراب می‌کند.
- پورت PostgreSQL در خروجی کاربر روی `0.0.0.0:5432` و `[::]:5432` منتشر است.
  این به‌تنهایی دسترسی اینترنتی از پشت فایروال را اثبات نمی‌کند، ولی همراه با
  تلاش‌های ورود نامعتبر نیازمند محدودسازی به شبکهٔ داخلی/مبدأهای مجاز است.
  تغییر پورت DB و restart آن را وسط سفارش با این اصلاح منابع مخلوط نکنید.
