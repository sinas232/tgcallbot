# نسخهٔ ۲.۲.۱۷ — «تا پایان زمان سفارش بمانند»؛ حذف لغو خودکار و تحمل شبکهٔ WARP

> **خلاصهٔ یک‌خطی:** علتِ لغو شدن سفارش‌ها چند دقیقه بعد از شروع پیدا و حذف شد؛ از این نسخه هیچ سفارشی
> به‌خاطر «کم بودن تعداد اکانت» یا پرش شبکه بسته نمی‌شود و اکانت‌ها تا پایان زمان خریداری‌شده در تماس/GROUP می‌مانند.

---

## ۱) ریشهٔ مشکل چه بود؟

پایانِ «فاز ورود» (Build) یک شرط قطعی داشت:

```python
if live < requested:                      # ❌ نسخه‌های قبل
    await self._fail_order(order_id, "Requested account count could not be delivered.")
```

یعنی به‌محض تمام شدنِ مرحلهٔ ورود، اگر تعداد اکانت‌های «شناسایی‌شده به‌عنوان حاضر» کمتر از تعداد سفارش
بود، **کل سفارش لغو و تسویه** می‌شد.

چرا این اتفاق «حدود ۵ دقیقه بعد از شروع» می‌افتاد؟

- ورود انبوه اکانت‌ها با فاصله و تأییدِ حضور انجام می‌شود؛ روی شبکهٔ WARP این فاز به‌طور طبیعی چند دقیقه طول می‌کشد.
- در همان لحظه، شمارشِ «حضور» می‌تواند موقتاً کمتر از واقعیت باشد (پرش شبکه، پاسخ دیرِ تلگرام، ری‌استارت سشن).
- نتیجه: سفارش دقیقاً همان لحظه لغو می‌شد و بعد از آن، اکانت‌ها «پشت‌سرهم» از ویس‌کال و گروه بیرون می‌آمدند.

---

## ۲) رفتار جدید (نسخهٔ ۲.۲.۱۷)

| وضعیت پایان فاز ورود | رفتار |
|---|---|
| همهٔ اکانت‌ها وارد شدند | مانند قبل: تا پایان زمان، سرویس ادامه دارد |
| **بخشی** از اکانت‌ها وارد شدند | **سفارش لغو نمی‌شود**؛ تا پایان زمان خریداری‌شده ادامه می‌یابد و تکمیل/جایگزینی فعال می‌ماند |
| شمارش لحظه‌ای «حضور» صفر گزارش دهد ولی اکانت‌ها وارد‌شده باشند | سفارش ادامه می‌یابد (تعداد اکانت‌های واقعاً وارد‌شده بر تشخیص لحظه‌ای اولویت دارد) |
| **هیچ** اکانتی وارد نشده باشد | سفارش تسویه و **کل مبلغ عودت** می‌شود (خدمتی ارائه نشده) |

- پیام اطلاع‌رسانی یک‌باره برای مشتری: «⚠️ سفارش #X: در حال حاضر N از M اکانت داخل تماس/گروه هستند.
  سفارش لغو نشد و تا پایان زمان خریداری‌شده فعال می‌ماند…». این پیام ضد تکرار است (claim دیتابیسی).
- محاسبهٔ مالی دست‌نخورده است: مبنای محاسبه همان **زمان فعال سفارش** (نسخهٔ ۲.۲.۱۴) است و در صورت لغو،
  فقط زمان استفاده‌شده کسر می‌شود.

---

## ۳) تحمل شبکهٔ WARP

کل ترافیک این ربات از WARP عبور می‌کند و WARP می‌تواند پرش‌های کوتاه داشته باشد. برای اینکه این پرش‌ها
هیچ‌وقت باعث خروج اشتباه اکانت نشوند:

- **آستانهٔ «غیبت تأییدشده»** از ۵ چرخه به **۸ چرخه** افزایش یافت (≈ ۱ دقیقه غیبتِ متوالی و تأییدشده).
  فقط پس از این حد، بازیابی همان اکانت انجام می‌شود و تا ۳ تلاش ناموفق هم چیزی از گروه حذف نمی‌شود.
- خطا/بی‌پاسخ بودن API ⇒ حالت `TEMPORARILY_UNKNOWN`؛ نه شمارش کم می‌شود، نه اقدامی انجام می‌شود.
- اگر رسانهٔ صوتی از دست برود ولی حضور در تماس تأیید شود (خطای رایج WARP) ⇒ اکانت **شمارش می‌شود** و
  فقط یک بازیابیِ محدود و زمان‌بندی‌شده برای رسانه انجام می‌شود؛ هیچ خروج/ورود پرسرعت رخ نمی‌دهد.
- خروج اکانت‌ها از گروه همچنان (نسخهٔ ۲.۲.۱۶) **یک روز بعد و فقط اگر سفارشی برای همان گروه نباشد** انجام می‌شود.

- **جایگزینی «قطره‌ای»:** در هر چرخهٔ نگهداری حداکثر ۲ اسلات رها/جایگزین می‌شود
  (`VOICE_MAX_RELEASES_PER_CYCLE`) تا در قطعیِ شبکهٔ WARP، اکانت‌ها پشت‌سرهم از تماس بیرون نیفتند.
  خط لاگ هشدار هم ثبت می‌شود: `N slot(s) flagged unrecoverable at once — releasing at most 2 this cycle (possible network incident)`.
- **بازبینی اسلات‌های در‌انتظار جایگزینی:** هر ۳ چرخه (~۳۰ ثانیه) دوباره بررسی می‌شوند
  (`VOICE_UNRECOVERABLE_RECHECK_CYCLES`)؛ اگر شبکه برگشته باشد، همان اکانت سالم شناخته می‌شود و
  از خروج/جایگزینی نجات می‌یابد (به‌جای «رها شدن برای همیشه»).

### کلیدهای .env مربوط به WARP

```env
# تعداد چرخهٔ متوالیِ «غیبت تأییدشده» پیش از هر بازیابی/جایگزینی (پیش‌فرض: 8)
CONFIRMED_DISCONNECT_THRESHOLD=8
# حداکثر رهاسازی/جایگزینی در هر چرخه (ضد خروج پشت‌سرهم)
VOICE_MAX_RELEASES_PER_CYCLE=2
# هر چند چرخه اسلات‌های در‌انتظار جایگزینی دوباره بررسی شوند
VOICE_UNRECOVERABLE_RECHECK_CYCLES=3

# اگر بخواهید خروج‌ها محافظه‌کارانه‌تر و با فاصلهٔ بیشتری انجام شوند:
# VOICE_LEAVE_STAGGER_MIN=2
# VOICE_LEAVE_STAGGER_MAX=6
# VOICE_LEAVE_MAX_CONCURRENCY=2

# مهلت خروج از گروه (نسخهٔ ۲.۲.۱۶) — پیش‌فرض یک روز:
GROUP_LEAVE_DELAY_MINUTES=1440
```

## ۴) چه چیزی برای عیب‌یابی در لاگ اضافه شد؟

- در پایان فاز ورود، تعداد واقعی و درخواستی همیشه لاگ می‌شود:
  `Order X: 3/5 account(s) present after build — order continues to the end of its purchased duration (no auto-cancel)`
- دیگر هیچ لاگِ `Requested account count could not be delivered` وجود ندارد؛ اگر سفارشی تسویه شود،
  دلیلش در لاگ و در گزارش مشتری صریح است (`No account could be delivered`).

برای بررسی سلامت: `docker compose logs bot --tail=300 | grep -E "no auto-cancel|No account could be delivered|deferred group leave"`

## ۵) تست‌ها

- ۱۶ تست جدید در `tests/test_no_early_cancel.py`: ادامهٔ سفارش با تحویل ناقص، ادامه با شمارش صفرِ لحظه‌ای،
  عودت کامل در حالت «هیچ اکانتی وارد نشد»، پیام یک‌بارهٔ کمبود تعداد، جایگزینی قطره‌ای (حداکثر ۲ در هر چرخه)،
  بازبینی اسلات‌های در‌انتظار جایگزینی و مستندسازی کلیدهای WARP.
- همهٔ تست‌های نسخه‌های ۲.۲.۱۴ تا ۲.۲.۱۶ (حسابداری زمان فعال، سقف ۵ سفارش هم‌پوشان، خروج تأخیری از گروه) سبز مانده‌اند.
- مجموع کل: **۴۳۱ تست موفق بدون skip**، شامل **۴۹ تست PostgreSQL واقعی**.

## ۶) دستورات نصب

```bash
cd /root/tgcallbot

# ۱) پشتیبان‌گیری
docker compose exec -T db pg_dump -U postgres tgcallbot > backup-$(date +%F-%H%M).sql

# ۲) دریافت نسخهٔ جدید
git fetch origin
git switch arena/01a0b5c9-tgcallbot 2>/dev/null || git switch -c arena/01a0b5c9-tgcallbot origin/arena/01a0b5c9-tgcallbot
git pull --ff-only

# ۳) افزودن کلیدهای جدید (اختیاری — پیش‌فرض‌ها امن هستند)
grep -q CONFIRMED_DISCONNECT_THRESHOLD .env || cat >> .env <<'EOF'

CONFIRMED_DISCONNECT_THRESHOLD=8
GROUP_LEAVE_DELAY_MINUTES=1440
GROUP_LEAVE_POLL_MINUTES=5
GROUP_LEAVE_BATCH_LIMIT=200
GROUP_LEAVE_MAX_ATTEMPTS=3
EOF

# ۴) بازسازی و اجرا
docker compose up -d --build --no-deps bot
docker compose logs -f bot --tail=100
```

پس از نصب، در لاگ خط شروع نسخه را ببینید: `BOT_VERSION = 2.2.17`.
